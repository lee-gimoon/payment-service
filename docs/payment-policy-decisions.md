# 결제 기획 정책 결정표

- 작성일: 2026-09-10
- 문서 상태: 사업 정책 결정을 위한 제안서
- 관련 문서: [도메인 개요](payment-domain.md) · [실무 시나리오](payment-scenarios.md)

아직 업종이 정해지지 않았으므로 아래 내용은 **확정 정책이 아니다**. `제안`은 첫 구현의 기준안, `결정 필요`는 실제 상품·사업 조건을 알아야 정할 수 있는 항목이다. 정책의 책임자는 역할로 표시했으며, 소규모 사업에서는 한 사람이 여러 역할을 맡을 수 있다.

## 1. 사업과 결제 범위

| ID | 결정 항목 | 초기안·확인할 내용 | 상태 | 담당 역할 |
| --- | --- | --- | --- | --- |
| P01 | 판매 주체 | 단일 사업자가 직접 판매. 입점 판매자 배분은 별도 확장 | 제안 | 사업 |
| P02 | 상품 유형 | 학습은 실물 상품. 실제 판매상품·제공 방식은 선택 필요 | 결정 필요 | 사업 |
| P03 | 거래 통화·지역 | 국내 KRW, 원 단위 금액 | 제안 | 사업·재무 |
| P04 | 청구 방식 | 주문 1건에 일회성 PG 전액 수납. 분할 수납 제외 | 제안 | 기획 |
| P05 | 결제수단 | 카드·간편결제 우선. 실제 계약 가능 수단 확인 | 제안 | 사업·개발 |
| P06 | 결제 UI | 토스 주문서형 결제를 후보로 사용 | 제안 | 기획·개발 |
| P07 | 회원·비회원 | 주문 소유권 확인 방식을 각각 마련. 실제 구매 정책과 심사 조건 확인 | 결정 필요 | 기획 |
| P08 | 0원 주문 | 첫 범위 제외. 도입 시 수납 없는 주문 완료 흐름 추가 | 제안 | 기획 |

제품 선택과 계약·심사 조건은 [토스 공식 결제제품 안내](https://docs.tosspayments.com/guides/v2/get-started/payment-products)를 확인한다. 특히 회원 정책은 개발 편의만으로 정하지 않고 실제 심사 요건과 맞춘다.

## 2. 주문·재고·재시도

| ID | 결정 항목 | 초기안·확인할 내용 | 상태 | 담당 역할 |
| --- | --- | --- | --- | --- |
| P09 | 가격 확정 시점 | 결제 시도 전에 서버가 최종 가격 저장. 변경 시 고객 재확인 | 제안 | 기획·개발 |
| P10 | 주문 유효시간 | 상품 특성에 맞는 기간, 만료 전 승인 처리 중인 주문의 보호 기준 | 결정 필요 | 기획·운영 |
| P11 | 재고 확보 | 승인 전에 한정 수량 확보. 확보·해제 시점과 유지시간 결정 | 결정 필요 | 상품·운영 |
| P12 | 결제 재시도 | 앞선 시도의 미수납 확정 후 새 시도. 불확실한 동안 제한 | 제안 | 개발·운영 |
| P13 | 성공 수납 제한 | 한 주문에서 성공한 수납 시도는 하나. 전액 취소 후 재구매는 새 주문 | 제안 | 기획·개발 |
| P14 | 제공 실패 | 복구 가능한 제공 작업 재처리, 불가 시 보상 환불. 자동 처리 한도 결정 | 결정 필요 | 운영 |
| P15 | 가상계좌 도입 | 입금 기한, 재고 유지, 늦은 입금, 입금 취소 대응 후 활성화 | 결정 필요 | 기획·운영 |

토스의 인증 유효시간을 P10의 주문 유효시간이나 P11의 재고 확보시간으로 그대로 복사하지 않는다. 세 시간의 목적은 다르다. 학습 예시로 주문 만료를 30분으로 잡더라도 이는 PG의 결제 인증 유효시간에 대한 설명이 아니다.

## 3. 취소·반품·환불

| ID | 결정 항목 | 초기안·확인할 내용 | 상태 | 담당 역할 |
| --- | --- | --- | --- | --- |
| P16 | 출고 전 전액 취소 | 출고 중단과 취소 자격을 확인한 뒤 실행. 출고와의 동시 처리 기준 필요 | 제안 | 운영·기획 |
| P17 | 출고 후 반품 | 접수·회수·검수·환불 판단 기준, 고객 고지, 귀책 구분 | 결정 필요 | 사업·운영 |
| P18 | 부분 취소 | 첫 자동화 범위에서는 제외. 도입 전 상품·수량별 금액 배분 확정 | 제안 | 기획·재무 |
| P19 | 배송비 | 최초 배송비·회수비·무료배송 조건 변경·판매자 귀책 처리 | 결정 필요 | 운영·재무 |
| P20 | 쿠폰 | 최소 구매금액 재판정, 부분 취소 배분, 전체 취소 복원·유효기간 | 결정 필요 | 기획 |
| P21 | 포인트 | 사용·배분·복원·만료·적립 회수. 무상 적립과 충전금 구분 | 결정 필요 | 기획·재무 |
| P22 | 환불 승인 권한 | 본인 주문 요청, 운영 검토, 고액·예외 환불의 승인 기준 | 결정 필요 | 운영 |
| P23 | 환불 중복 방지 | 요청 식별자 유지, 진행 중 금액 확보, 불확실 시 잔액 보호 | 제안 | 개발 |
| P24 | 고객 안내 | 요청 접수·PG 처리 완료·실제 반영 안내를 구분 | 제안 | CS |
| P25 | 수동 환불 | 기존 PG 취소 확인, 지급 근거·담당자 기록, 중복 송금 방지 | 결정 필요 | 재무·운영 |

수단별 PG 취소 가능 기간과 고객의 반품·환불 권리는 별개의 검토 대상이다. PG 취소 기능을 쓸 수 없다는 사실만으로 고객 요청을 끝내지 말고 사업의 후속 처리 절차를 정한다. PG 제약은 [공식 취소 가이드](https://docs.tosspayments.com/guides/v2/cancel-payment)와 실제 상점 계약으로 확인한다.

## 4. 운영·정산·장애

다음 시간 값은 **운영 기준의 제안**이며 토스의 처리 보장이나 법정 기한이 아니다.

| ID | 결정 항목 | 초기안·확인할 내용 | 상태 | 담당 역할 |
| --- | --- | --- | --- | --- |
| P26 | 결과 재확인 | 초기 확인 후 간격을 늘려 조회. 예: 10초·30초·1분·5분. 장애 시 호출량 제한 | 제안 | 개발 |
| P27 | 장기 미확인 | 예: 10분 이상이면 운영 알림. 실패로 자동 확정하지 않고 조회·조사 유지 | 제안 | 운영·개발 |
| P28 | 환불 실패 대응 | 즉시 목록 등록, 영업 중 확인 주기·비영업 시간 책임자 결정 | 결정 필요 | 운영 |
| P29 | 대사 주기 | 일 1회 거래·취소·정산 대사, 최근 구간 중복 확인. 초기에는 수동 가능 | 제안 | 재무·개발 |
| P30 | 정산 계약 | 수단별 수수료, 관련 세금, 지급 주기·보류·취소 시 조정 확인 | 결정 필요 | 사업·재무 |
| P31 | 직접 관리자 취소 | PG 관리자 조치도 내부 취소 사유·주문 후속 처리와 연결 | 제안 | 운영 |
| P32 | 장애 중 판매 | PG·내부 저장 장애 시 신규 결제 제한 기준과 복구 담당자 | 결정 필요 | 운영·개발 |
| P33 | 분쟁·미인지 결제 | 고객 신고 접수, 제공·승인 증거 보존, PG 확인, 관련 거래 연결 | 결정 필요 | CS·운영 |

P26~P27은 **결과를 확인하는 작업**의 간격이다. 같은 간격으로 신규 승인·취소를 반복 실행하라는 뜻이 아니다. 상태와 오류 유형을 확인하고 기존 요청의 재처리가 가능한지 별도로 판단한다.

P30의 정산 주기와 수수료는 임의의 고정값으로 확정하지 않는다. [공식 정산 설명](https://docs.tosspayments.com/resources/glossary/settlement)을 참고하고 해당 상점 계약을 기록한다.

## 5. 출시 전에 확정할 운영 자료

| 항목 | 남길 결과물 | 담당 역할 |
| --- | --- | --- |
| 상품·사업 모델 | 실제 판매상품, 판매 주체, 제공 시점, 이용 조건 | 사업 |
| PG 계약·심사 | 상점·환경·사용 가능 수단·계약 조건 확인 기록 | 사업 |
| 고객 정책 | 취소·반품·환불·배송비 조건과 고객에게 표시할 문안 | 기획·운영 |
| 판매·개인정보 안내 | 사업자 정보, 문의 창구, 약관·처리방침의 적용 내용 | 사업·개인정보 담당 |
| 증빙·세금 | 과세 구분, 영수증·현금영수증 처리 방식 | 재무 |
| 구매안전 서비스 | 에스크로 등 적용 여부와 실제 제공·확정 처리 | 사업·운영 |
| 기록 보관 | 주문·거래·동의·감사·개인정보별 근거, 기간, 접근·삭제 기준 | 개인정보 담당·재무 |
| 장애 대응 | PG 성공/내부 실패, 미확인, 이중 결제·환불 조사 절차 | 개발·운영 |
| 검증 범위 | 테스트 가능 수단, 실제 환경 확인 항목, 결과 증거 | 개발·운영 |

업종이 정해지면 적용되는 규정·계약의 최신 원문을 확인해 각 결과물에 근거와 확인일을 기록한다. 이 표는 법적 의무 전체를 확정한 목록이 아니라 결제 출시를 위한 준비 항목이다.

## 6. 정책 결정 기록 양식

정책이 결정되면 아래 양식으로 남긴다. 과거 주문에 적용한 정책을 재현할 수 있도록 정책 버전과 적용 시작일을 관리한다.

| 필드 | 기록할 내용 |
| --- | --- |
| 정책 ID | 예: P19 배송비 |
| 최종 결정 | 고객 상황별 구체적인 처리 규칙 |
| 적용 범위 | 상품·결제수단·주문 조건 |
| 금액 예제 | 정상·부분 취소·전액 취소의 계산 |
| 예외 | 자동 처리하지 못하는 경우와 담당자 |
| 근거 | 사업 판단, 고객 안내, 해당 계약·공식 자료 |
| 담당·결정일 | 결정 책임자와 확인일 |
| 버전·적용일 | 새 주문부터 적용할지, 기존 주문 처리 원칙 |
| 검증 시나리오 | 연결된 실무 사례와 기대 결과 |

## 7. 구현에 들어갈 준비가 됐는지 확인

- [ ] 실제로 판매할 상품과 제공 방식이 정해졌다.
- [ ] 주문·결제·제공·환불의 상태와 책임을 설명할 수 있다.
- [ ] 첫 결제수단과 지원 범위가 정해졌다.
- [ ] 결제금액 산식과 가격 확정 시점이 정해졌다.
- [ ] 재고·주문 만료와 결제 결과 확인이 충돌할 때의 규칙이 있다.
- [ ] 취소 가능 판단과 반환 금액의 결정 주체가 정해졌다.
- [ ] 중복 승인·중복 환불·응답 유실의 기대 결과가 정해졌다.
- [ ] 자동화하지 않는 업무를 처리할 운영 경로가 있다.
- [ ] 누락 거래를 찾아 복구하고 정산 차이를 확인할 담당자가 있다.

학습용 구현은 위 제안 범위를 가정으로 명시하고 시작할 수 있다. 실제 판매를 위한 미결정 정책은 출시 전에 해소한다.
