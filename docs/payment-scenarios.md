# 결제 도메인 실무 시나리오

- 작성일: 2026-09-10
- 문서 상태: 기획 검토용 시나리오·인수 기준 초안
- 기준 문서: [온라인 결제 도메인 이해와 실무 기획](payment-domain.md)

이 문서는 구현 코드나 자동화 테스트가 아니라 **“이런 일이 발생하면 사업과 시스템은 어떤 결과를 보장해야 하는가”**를 설명한다. 상태 이름은 업무를 설명하기 위한 표현이다. 별도 표시가 없는 금액·시간·처리 방식은 학습용 예시 또는 설계 제안이다.

## 1. 정상 주문: 53,000원 카드 결제

**구매 내용:** 티셔츠 30,000원 + 모자 20,000원 + 배송비 3,000원. 할인 없음.

| 순서 | 행동·사건 | 기대 결과 |
| --- | --- | --- |
| 1 | 고객이 결제하기 선택 | 주문 당시 가격과 53,000원 청구금액 저장 |
| 2 | 첫 결제 시도 시작 | 주문과 시도, PG 주문번호 연결 |
| 3 | 카드 인증 후 상점으로 복귀 | 서버가 주문 당사자·시도·금액·재고 확인 |
| 4 | PG 승인 완료 확인 | 53,000원 수납과 PG 거래 기록 |
| 5 | 주문 확정 | 출고 대상 2개 생성, 결제 재시도 차단 |
| 6 | 배송 완료 | 배송 상태만 갱신, 승인 거래는 보존 |

**인수 기준**

- 성공 페이지를 새로고침해도 추가 청구와 중복 출고가 없다.
- 결제 직후 브라우저를 닫아도 고객은 주문 조회에서 결과를 확인한다.
- 현재 상품 가격을 바꿔도 이 주문의 구매금액은 53,000원으로 재현된다.
- PG 수납액과 고객 안내 금액, 주문이 요구한 PG 청구금액이 일치한다.

## 2. 출고 전 전액 취소

**시작 상태:** 53,000원 수납 완료, 상품 제공 미시작, 기존 환불 없음.

1. 고객이 주문 전체 취소를 요청한다.
2. 운영 정책에 따라 취소 자격을 확인하고 출고 진행을 막는다.
3. 53,000원 환불 요청을 생성하고 전액을 확보한다.
4. PG 취소 결과를 확인한다.
5. 취소 거래를 기록하고 주문 취소, 확보 재고 해제, 고객 안내를 처리한다.

**검산:** 최초 수납 53,000원 − PG 취소 53,000원 = 남은 결제금액 0원.

PG 응답이 유실되면 환불은 결과 확인 필요 상태다. 주문을 더 이상 제공하지 않기로 확정한 사실과 금융 처리의 미확정 상태를 함께 표시한다. 취소 완료를 확인하기 전 확보 금액을 해제하지 않으며, 고객에게 환불 완료라고 안내하지 않는다.

PG 취소 성공 후 내부 저장이 실패했다면 기존 취소 거래를 조회해 연결한다. 새 환불 요청을 만들어 같은 금액을 또 반환하지 않는다.

## 3. 할인과 포인트가 있는 부분 환불—확장 예제

이 예제는 첫 구현 범위 이후에 필요한 금액 정책을 이해하기 위한 것이다. **실제 적용할 할인·포인트·배송비 정책으로 확정된 내용은 아니다.**

가정은 다음과 같다.

- 티셔츠 30,000원, 모자 20,000원, 배송비 3,000원이다.
- 상점 쿠폰 5,000원과 무상 적립 포인트 2,000점을 사용한다. 1점은 결제 차감 시 1원으로 취급한다.
- 쿠폰과 포인트를 상품 가격 비율 3:2로 배분한다. 배송비에는 배분하지 않는다.
- 부분 취소 이후에도 기존 할인 조건은 유지한다.
- 모자만 출고 전에 취소한다. 티셔츠는 배송하므로 최초 배송비는 유지한다.

| 항목 | 상품·배송비 | 쿠폰 배분 | 포인트 배분 | PG 수납 배분 |
| --- | ---: | ---: | ---: | ---: |
| 티셔츠 | 30,000원 | 3,000원 | 1,200점 | 25,800원 |
| 모자 | 20,000원 | 2,000원 | 800점 | 17,200원 |
| 배송비 | 3,000원 | 0원 | 0점 | 3,000원 |
| 합계 | 53,000원 | 5,000원 | 2,000점 | 46,000원 |

### 모자만 취소하면

| 처리 대상 | 처리 결과 |
| --- | --- |
| PG | 모자에 배분된 17,200원 취소 |
| 포인트 | 사용했던 800점 복원 |
| 쿠폰 할인 | 모자 할인 2,000원을 현금으로 반환하지 않음 |
| 쿠폰 사용권 | 이 예제에서는 부분 취소 시 복원하지 않음 |
| 배송비 | 3,000원 유지 |
| 주문상품 | 모자는 취소, 티셔츠는 제공 대상 유지 |

**검산:** 46,000원 − 17,200원 = 28,800원. 남은 PG 금액은 티셔츠 25,800원 + 배송비 3,000원과 일치한다. 사용 포인트 잔량은 2,000점 − 800점 = 1,200점이다.

모자의 표시 가격이 20,000원이라고 PG에서 20,000원을 취소하면 할인·포인트 배분과 맞지 않는다. 반대로 현금성 반환액만 보여주면 고객은 포인트 복원을 놓칠 수 있으므로 안내를 나눠 보여준다.

이후 출고 전에 티셔츠까지 취소해 전체 주문을 끝낸다고 가정하면, 나머지 PG 금액 28,800원과 포인트 1,200점을 반환한다. 누적 반환은 PG 46,000원과 포인트 2,000점이다. 쿠폰은 별도의 재발급·유효기간 정책에 따른다.

### 실제로 더 결정해야 하는 사항

비율 배분 결과 1원 미만이 발생하면 절사 후 남은 원을 어떤 상품·수량에 배정할지 결정하고 최초 배분을 보존한다. 마지막 취소에서는 미반환 잔액을 기준으로 검산한다. 과세·면세가 섞인 경우 취소 상품의 세금 구성도 함께 계산한다.

최소 주문금액 쿠폰이나 무료배송 조건을 취소 후 다시 적용한다면 위 계산은 달라진다. 그 경우 변경되는 고객 부담과 반환 산식을 결제 전 정책에 명시해야 한다. 정책을 먼저 정한 뒤 해당 정책으로 예제를 다시 계산한다.

## 4. 결제·취소의 예외 상황 검토표

| ID | 상황 | 기대하는 업무 처리 | 금지할 결과 |
| --- | --- | --- | --- |
| E01 | 고객이 결제 버튼을 연속 클릭 | 같은 주문의 활성 시도를 확인하고 중복 진행 제한 | 같은 주문 이중 수납 |
| E02 | 승인 완료 페이지 새로고침 | 저장된 결과를 반환하거나 기존 시도를 재확인 | 새 승인·출고 작업 생성 |
| E03 | PG 승인 후 통신 시간 초과 | 기존 시도를 결과 확인 필요로 유지하고 조회 | 즉시 실패 처리 후 재결제 유도 |
| E04 | PG 성공 후 내부 DB 저장 실패 | 저장된 요청·식별자로 승인 결과 복구 | 결제된 고객 주문을 삭제 |
| E05 | PG가 카드 한도 부족 등으로 확정 거절 | 실패 이유 안내 후 새 시도 허용 | 기존 실패 이력 덮어쓰기 |
| E06 | 브라우저가 청구금액 변조 | 서버 주문금액과 불일치하면 승인 중단 | 변조 금액으로 상품 제공 |
| E07 | 타인의 주문번호로 승인·취소 요청 | 소유권·운영 권한 검증 실패로 거절 | 주문번호만으로 금전 처리 |
| E08 | 승인 직전 마지막 재고가 소진 | 재고 확보 여부를 확인해 승인 진행 결정 | 제공 가능성 검토 없이 승인 |
| E09 | 승인 성공 후 제공 불가능 판명 | 먼저 중복 없는 복구를 시도하고, 복구 불가 시 보상 환불 절차 | 돈을 받은 채 주문을 실패로만 표시 |
| E10 | 동일 웹훅이 여러 번 도착 | 같은 거래 반영과 후속 작업을 중복 방지 | 중복 이용권·중복 포인트 |
| E11 | 부분 취소 후 오래된 완료 알림 도착 | PG 현재 상태와 취소 이력을 확인 | 잔액을 최초 승인금액으로 복원 |
| E12 | 웹훅이 도착하지 않음 | 조회·대사로 누락 발견 및 복구 | 영구적인 결제 확인 중 |
| E13 | 운영자 두 명이 동시에 부분 환불 | 진행 중 확보액까지 포함해 잔액 검증 | 총 반환액이 수납액 초과 |
| E14 | 환불 요청 직후 응답 유실 | 같은 요청과 키로 기존 거래 확인 | 새 키로 별도 환불 실행 |
| E15 | PG 관리자에서 직접 취소 | PG 거래와 내부 주문을 연결해 후속 처리·감사 기록 | 내부에서 계속 수납 완료로 방치 |
| E16 | 가상계좌만 발급 | 입금 대기 안내, 제공 시작 금지 | 계좌 발급을 결제 완료로 처리 |
| E17 | 주문 만료와 입금이 거의 동시 발생 | PG 입금 확인 후 공급 가능성에 따라 확정 또는 환불 처리 | 입금 기록 없이 재고 해제·주문 삭제 |
| E18 | 가상계좌 입금 오류로 완료 상태가 되돌아감 | PG 재조회, 미출고분 보류, 제공된 건 운영 조사 | 오래된 알림이라고 일괄 무시 |
| E19 | 출고 처리와 취소 요청이 동시에 진행 | 주문상품별 처리 권한을 조정하고 먼저 확정된 사실 확인 | 출고·미출고 전액 취소 모두 무조건 실행 |
| E20 | PG 취소 실패 후 수동 계좌 반환 검토 | 원거래·실패 근거·기존 수동 지급을 확인하고 예외 이력 연결 | PG 재시도와 수동 송금 동시 실행 |

E15는 PG의 모든 관리자 동작을 특정 웹훅으로 반드시 수신한다는 가정이 아니다. 적용 가능한 알림과 주기적 대사를 함께 사용한다. E18의 실제 상태 전이와 이벤트 범위는 [공식 웹훅 이벤트 문서](https://docs.tosspayments.com/reference/using-api/webhook-events)를 따른다.

## 5. 부분 환불의 동시 요청

**시작 상태:** 최초 수납 53,000원, 완료된 취소 0원.

1. 운영자 A가 30,000원 환불 요청을 생성하고 해당 금액을 확보한다.
2. 운영자 B가 같은 결제에 30,000원 환불을 요청한다.
3. 새로 사용할 수 있는 금액은 53,000 − 0 − 30,000 = 23,000원이므로 B의 요청은 진행할 수 없다.
4. A가 PG 취소를 완료하면 완료된 취소 30,000원, 진행 중 확보 0원, 잔액 23,000원이 된다.
5. A의 실패가 확정되면 확보한 금액을 해제한다. A의 결과가 불확실하다면 확보를 유지한다.

**인수 기준:** 두 요청이 거의 동시에 들어와도 위 규칙을 만족한다. 화면에 잔액을 표시하는 것만으로 충분하지 않고, 실행하는 시점에도 중복 확보를 막아야 한다.

## 6. 정산 차이를 발견한 운영자

**상황:** 내부에는 53,000원 승인 거래가 있는데 PG 정산 목록에서 같은 날짜에 바로 찾을 수 없다.

1. 결제·거래 식별자, 상점, 통화, 실제 승인 시각을 확인한다.
2. 정산 대상 기준일, 지급 예정일, 아직 정산 대상이 아닌 거래인지 확인한다.
3. 취소·보류·조정 기록과 수수료 내역을 확인한다.
4. 조회 범위가 달랐는지, 실제 누락인지 구분한다.
5. 차이가 남으면 근거 자료와 담당자를 지정하고 해결 결과를 기록한다.

“오늘 결제했으니 오늘 입금돼야 한다”는 기준으로 누락을 판정하지 않는다. [공식: 정산 기준과 지급 주기](https://docs.tosspayments.com/resources/glossary/settlement)

**인수 기준:** 차이 건에는 조사 사유, 대상 거래, 예상액·실제액, 담당자, 다음 확인 시각, 종료 근거가 있다. 단순히 숫자를 맞추려고 승인·취소 이력을 수정하지 않는다.

## 7. 구현 전에 답할 수 있어야 하는 질문

- 고객이 53,000원을 결제했다고 할 때 어떤 기록으로 사실을 확인하는가?
- 카드 인증만 성공한 고객과 승인이 완료된 고객을 어떻게 구분하는가?
- PG는 성공했는데 우리 저장이 실패하면 어디서 복구를 시작하는가?
- 다른 카드로 재시도해도 되는 시점을 누가 어떤 근거로 결정하는가?
- 2개 상품 중 1개를 취소할 때 할인·포인트·배송비를 어떻게 나누는가?
- 이미 진행 중인 환불과 신규 환불이 같은 잔액을 사용하지 않게 하는 규칙은 무엇인가?
- 결제 완료 후 상품 제공에 실패한 주문을 누가 찾아 처리하는가?
- PG 취소 완료와 고객 카드·계좌 반영을 어떻게 안내하는가?
- PG 관리자에서 직접 변경된 거래와 PG에만 존재하는 거래도 발견할 수 있는가?
- 고객 결제와 사업자 계좌 입금을 어떤 근거로 연결하는가?

답이 불명확한 항목은 [정책 결정표](payment-policy-decisions.md)에 남긴 뒤 설계한다.
