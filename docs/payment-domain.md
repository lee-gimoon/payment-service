# 결제 서비스 개발 계획과 기본 개념

## 1. 소프트웨어는 어떤 방식으로 개발하나요?

전 세계 소프트웨어 개발 현장에서 전체 개발 과정을 설명할 때 널리 사용하는 개념이 **SDLC(Software Development Life Cycle, 소프트웨어 개발 생명주기)**입니다. 웹 서비스도 이 생명주기를 따라 기획하고, 만들고, 운영하며 개선합니다.

```text
기획 → 요구사항 정의 → 설계 → 구현 → 테스트 → 배포 → 운영·피드백 → 개선
```

SDLC는 전체 과정을 나타내는 큰 틀이며, **그 과정을 어떻게 진행하느냐에 따라 여러 개발 방식**이 있습니다. 대표적인 예는 다음과 같습니다. [AWS의 SDLC 설명](https://aws.amazon.com/ko/what-is/sdlc/)

| 방식 | 진행하는 방법 |
| --- | --- |
| 폭포수(Waterfall) | 요구사항과 설계 등 앞 단계를 마친 뒤 다음 단계로 순서대로 진행합니다. |
| 애자일(Agile) | 작은 기능을 만들어 확인하는 과정을 짧게 반복하고, 피드백에 따라 요구사항과 계획을 조정합니다. |

웹 서비스 개발에서도 애자일 방식을 많이 활용합니다. 사용자 반응을 확인하며 기능을 자주 추가하고 수정하는 서비스에 잘 맞기 때문입니다.

### 애자일 방식이란?

**작게 만들고, 직접 사용해보고, 배운 내용을 다음 개발에 반영하는 방식**입니다. 동작하는 소프트웨어를 자주 제공하고 사용자와 소통하며, 변화에 맞춰 계획을 조정하는 것을 중요하게 생각합니다. [애자일 원칙](https://agilemanifesto.org/iso/ko/principles.html)

이 프로젝트에서는 **작은 MVP를 만들어 사용해보고, 피드백에 따라 보완하는 흐름**으로 애자일을 적용합니다.

```text
초기 MVP 범위 정하기 → 구현하며 확인하기 → 사용·피드백 → 필요한 개선 반복
```

MVP(최소 기능 제품)는 핵심 가정을 확인하고 사용자에게서 배우기 위해 만드는 작은 제품입니다. 우리 프로젝트에서는 ‘주문부터 결제 결과 확인까지 가능한 테스트 서비스’를 초기 MVP로 잡습니다. [Agile Alliance의 MVP 설명](https://agilealliance.org/glossary/mvp/)

**MVP는 처음 검증할 제품의 범위이고, 애자일은 개발하면서 배우고 계획을 조정하는 방식**입니다. MVP를 만드는 동안에도 작은 작업을 자주 실행·검증하고, 발견한 내용에 따라 요구사항과 설계를 수정합니다. MVP가 반드시 한 번의 반복 안에 완성되어야 하는 것은 아닙니다.

아래에서는 **초기 MVP의 전체 목표와 필요한 내용**을 먼저 정리합니다. 이후에는 MVP를 사용하며 확인한 문제와 필요에 따라 내용을 보충합니다.

## 2. 초기 MVP: 주문부터 결제 결과 확인까지

### 2.1. 목표와 범위

티셔츠 한 장을 **10,000원**에 파는 작은 쇼핑몰을 생각해봅시다. 고객은 카드로 결제하고 나중에 티셔츠를 배송받습니다.

고객은 “내 결제가 완료됐는지” 확인하고 싶고, 판매자는 “어떤 주문의 결제가 완료됐는지” 정확히 알아야 합니다. 그래서 **고객이 주문하고 결제한 뒤, 그 결과를 확인할 수 있는 서비스**를 만듭니다.

초기 MVP의 목표는 다음 사용자 흐름 전체가 동작하는 것입니다.

```text
티셔츠 1장 주문
→ 토스페이먼츠 결제창에서 카드 인증
→ 우리 Spring 서버에서 주문·금액 검증 후 결제 승인 요청
→ 토스페이먼츠·카드사에서 결제 승인 처리
→ 우리 Spring 서버에 승인 결과 저장
→ 결제 결과 조회
```

**확인하려는 것:** 고객 역할로 주문과 테스트 결제를 진행한 뒤, 결제 결과를 이해하고 다시 조회할 수 있는지 확인합니다. 판매자 역할에서는 저장된 주문과 PG 결제 결과가 일치하는지 확인합니다. 초기에는 우리가 두 역할로 직접 사용해보고, 이후 테스트 사용자의 의견을 받아 보완합니다.

| 구분 | 초기 MVP 범위 |
| --- | --- |
| 상품·주문 | 티셔츠 1종, 수량 1장, 10,000원으로 고정합니다. 배송비와 할인은 제외합니다. |
| 결제 | 토스페이먼츠 테스트 환경에서 카드 인증을 진행하고, 우리 Spring 서버가 토스페이먼츠에 결제 승인을 요청합니다. |
| 화면 | 주문 내용과 결제 버튼을 표시하고, 결제 결과 확인과 재조회 기능을 제공합니다. |
| 결과 처리 | 주문·결제 정보를 저장하고, 결제 성공·명확한 실패·결과 확인이 필요한 상태를 구분합니다. |
| 기본 검증 | Spring 서버에서 주문·금액을 검증하고, 중복·동시 요청을 제어하며, 결과가 불명확한 결제를 확인할 방법을 갖춥니다. |

독립 결제 서비스 안에 예제용 최소 주문 기능을 함께 둡니다. 전액 취소, 상품 관리, 배송 연동, 부분 취소, 정산 관리는 MVP 이후의 개선 후보로 둡니다.

### 2.2. MVP를 이해하는 데 필요한 결제 도메인

**도메인**은 “결제 업무에서 사용하는 개념과 규칙”이라는 뜻입니다. 이 개념들을 바탕으로 MVP의 화면, API, 데이터와 결과 처리 방식을 정합니다.

#### 토스페이먼츠는 어떤 역할을 하나요?

결제에는 다음 참여자가 있습니다.

| 참여자 | 하는 일 |
| --- | --- |
| 고객 | 상품을 고르고 카드로 결제합니다. |
| 우리 쇼핑몰 | 주문과 가격을 저장하고, 결제를 요청하고, 결과를 기록합니다. |
| 토스페이먼츠 | 쇼핑몰과 카드사 사이에서 결제 처리를 연결합니다. |
| 카드사 | 카드 사용자의 인증과 결제 승인 등을 처리합니다. |

이때 토스페이먼츠와 같은 결제 대행사를 **PG**라고 부릅니다. 우리 쇼핑몰은 토스페이먼츠와 연동해 카드 결제를 받을 수 있습니다. [토스 공식 설명](https://docs.tosspayments.com/resources/glossary/card-payment)

#### 주문부터 결제 완료까지

1. **고객이 주문합니다.** 우리 서버에 “티셔츠 1장, 10,000원, 결제 대기”로 저장합니다.
2. **결제 화면을 엽니다.** 고객이 결제하기 버튼을 누르면 토스페이먼츠의 결제 화면으로 진행합니다.
3. **고객이 카드 인증을 합니다.** 결제창이나 카드 앱에서 필요한 인증 정보를 입력합니다. 아직 우리 쇼핑몰의 결제 처리가 끝난 것은 아닙니다.
4. **우리 Spring Boot 서버가 결제 승인을 요청합니다.** 저장된 주문과 결제 금액이 맞는지 검증한 뒤 토스페이먼츠 승인 API를 호출합니다.
5. **토스페이먼츠와 카드사가 결제 승인을 처리합니다.** 우리 서버가 결제를 직접 승인하는 것이 아닙니다. 토스페이먼츠가 카드사에 승인을 요청하고 처리 결과를 우리 서버에 돌려줍니다.
6. **우리 Spring Boot 서버가 승인 결과를 확인하고 저장합니다.** 결제가 성공한 것을 확인하면 해당 주문을 “결제 완료”로 기록하고 고객에게 보여줍니다.

**카드 인증을 마친 것과 결제가 최종 완료된 것은 구분해야 합니다.** 여기서 “우리 서버”는 이 프로젝트에서 만드는 Spring Boot 서버를 뜻합니다. 우리 서버는 주문과 금액을 검증하고 승인을 요청하며, 실제 승인은 토스페이먼츠와 카드사가 처리합니다. 우리 서버가 그 결과를 확인하고 저장해야 결제 흐름이 끝납니다. [토스 공식 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

#### 결제했다고 배송과 입금까지 끝난 건가요?

주문 하나에도 서로 다른 일이 진행됩니다.

| 개념 | 확인하려는 것 | 티셔츠 예시 |
| --- | --- | --- |
| 주문 | 무엇을 얼마에 구매했나요? | 티셔츠 1장, 10,000원 |
| 결제 | 고객의 결제가 완료됐나요? | 카드 결제 승인 완료 |
| 상품 제공 | 고객에게 상품을 전달했나요? | 티셔츠 배송 완료 |
| 정산 입금 | 판매대금이 사업자 계좌에 들어왔나요? | 수수료 등을 반영한 금액 입금 |

**결제 완료와 상품 제공 완료:** 월요일에 결제하고 수요일에 티셔츠를 받는다면, 월요일에는 결제만 완료된 상태입니다. 결제 후 배송에 문제가 생기면 “결제 완료, 배송 문제 발생”으로 기록하고 해결해야 합니다.

온라인 강의라면 배송 대신 이용권 발급이 상품 제공에 해당합니다. 결제는 성공했지만 이용권 발급이 실패할 수도 있습니다.

**결제 완료와 정산 입금:** 고객이 월요일에 카드로 결제해도, 사업자 계좌에는 계약에서 정한 정산 일정에 따라 대금이 들어옵니다. 결제 금액에서 수수료 등이 반영되므로 고객이 결제한 금액과 사업자가 받는 금액도 다를 수 있습니다. [토스 공식 정산 설명](https://docs.tosspayments.com/resources/glossary/settlement)

이 구분은 설계에도 이어집니다. **결제 상태, 배송 상태, 정산 상태를 각각 관리**해야 한쪽의 문제를 다른 쪽의 실패로 잘못 처리하지 않습니다. 지금은 주문·결제만 구현하고, 배송·정산 기능을 추가할 때 별도의 상태를 설계합니다.

### 2.3. MVP에 필요한 기능과 설계

화면, API, 데이터가 위의 사용자 흐름을 함께 지원하도록 설계합니다. 아래는 MVP 전체의 초기 설계안입니다. 요청·응답 필드와 세부 상태 규칙은 해당 기능을 구현하면서 구체화하고 갱신합니다.

| 기능 | 화면과 서버가 할 일 |
| --- | --- |
| 주문 만들기 | 화면에 티셔츠 1장과 10,000원을 표시합니다. 서버가 주문번호와 금액을 결정해 저장합니다. |
| 결제 진행하기 | 저장된 주문으로 토스페이먼츠 결제창을 엽니다. 카드 인증 후 전달받은 정보를 서버로 보냅니다. |
| 승인·결과 저장 | 우리 Spring Boot 서버가 주문과 금액을 검증하고 토스페이먼츠에 승인을 요청합니다. 토스페이먼츠와 카드사가 처리한 결과를 받아 주문에 연결해 저장합니다. |
| 결과 확인하기 | 화면에 결제 성공·명확한 실패·결과 확인이 필요한 상태를 구분해 보여주고, 주문번호로 저장된 결과를 다시 조회할 수 있게 합니다. |

우리 서비스의 MVP API는 다음과 같이 구현했습니다. 요청·응답 예시와 실행 방법은 [README](../README.md#구현된-mvp)를 참고합니다.

| API | 역할 |
| --- | --- |
| `POST /orders` | 주문을 생성하고 주문번호와 주문 내용을 `201`로 응답합니다. |
| `POST /payments/confirm` | 인증 결과로 받은 `orderId`, `paymentKey`, `amount`를 검증하고, 토스페이먼츠 승인 API를 호출한 뒤 결과를 저장합니다. |
| `GET /orders/{orderId}` | 주문 내용과 연결된 결제 상태를 조회해 `200`으로 응답합니다. |
| `POST /payments/{orderId}/reconcile` | 확인이 필요한 결제를 PG에서 조회하고 저장합니다. 재승인은 요청하지 않습니다. |
| `GET /payment-config` | 브라우저에서 사용할 테스트 클라이언트 키와 결제 사용 가능 여부만 반환합니다. |

요청 형식이나 값이 잘못되면 `400`, 존재하지 않는 주문은 `404`로 응답합니다. 승인 API는 성공 `200`, 명확한 거절 `422`, 처리 중·결과 확인 필요 `202`로 응답하며 모두 주문과 결제 상태를 포함합니다. 다른 결제 키로 기존 시도를 교체하거나 다른 주문에 연결된 키를 재사용하면 `409`, 키 설정 누락이나 DB 저장 장애는 `503`으로 응답합니다.

주문 생성은 빈 본문 또는 `{}`만 받으며 상품·수량·가격을 서버에서 결정합니다. 승인 요청은 `orderId`, `paymentKey`, 양의 정수 금액 `amount`를 받습니다. 저장된 금액뿐 아니라 PG 응답의 주문번호·결제 키·금액·통화·카드 수단·승인 상태·승인 시각도 확인합니다.

| 결제 상태 | 구현된 의미 |
| --- | --- |
| `READY` | 저장된 주문은 있지만 승인 시도는 없습니다. |
| `PROCESSING` | 승인 요청이나 PG 재조회를 수행 중입니다. |
| `SUCCEEDED` | PG의 `DONE` 상태와 일치하는 결제 정보를 확인했습니다. |
| `FAILED` | 명시적인 카드 거절 또는 PG의 `ABORTED`/`EXPIRED`를 확인했습니다. |
| `UNKNOWN` | 결과가 불명확하여 PG 조회로 재확인이 필요합니다. |

초기 MVP에서는 주문당 승인 시도 하나만 허용합니다. 동일 결제 키의 중복 요청에는 기존 결과를 반환하고, 다른 키로 시도를 교체하지 않습니다. 확정 실패 후에는 새 주문으로 다시 진행합니다. 카드 인증 실패 리다이렉트만으로 DB 상태를 실패 처리하지 않습니다.

| 데이터 | 저장할 핵심 내용 |
| --- | --- |
| 주문 | 주문번호, 상품명, 수량, 주문 금액, 생성 시각을 저장합니다. 주문번호에는 중복 방지 제약조건을 둡니다. |
| 결제 | 연결된 주문, 결제 시도 식별 정보, PG의 `paymentKey`, 결제 금액, 상태, 결과 확인 시각을 저장합니다. 중복 요청 처리와 결과 재확인에 필요한 정보도 보관합니다. |

**MVP에서도 지킬 결제 규칙:** 가격은 서버가 결정하고 승인 전에 저장된 금액과 비교합니다. PG로부터 승인 성공 결과를 확인한 뒤 결제 완료로 기록하며, 같은 주문의 중복·동시 요청을 제어합니다. 통신 시간 초과처럼 결과가 불명확하면 “확인 필요”로 남기고 PG 조회로 확인합니다. PG에서 승인을 처리한 뒤 DB 저장에 실패해도 복구할 수 있도록 요청 식별 정보를 PG 호출 전에 저장합니다.

구현에서는 주문 행 잠금으로 시도를 선점하고 결제 키·금액·결제 시도 UUID를 먼저 커밋합니다. 그 UUID를 PG 승인 요청의 `Idempotency-Key`로 사용합니다. PG 네트워크 요청과 결과 저장은 별도 단계이므로 네트워크를 기다리는 동안 DB 잠금을 유지하지 않습니다. 주문당 결제 한 건, 결제 키 유일성, 주문·결제 금액 일치를 Flyway의 DB 제약조건으로 관리합니다.

승인 이후 저장 실패 또는 프로세스 종료로 남은 `PROCESSING`은 작업 시작 30초 후 조회 응답에서 `UNKNOWN`으로 표시하고 수동 PG 조회를 허용합니다. DB 행은 복구 전까지 `PROCESSING`일 수 있습니다. 재조회마다 작업 UUID를 새로 발급해 이전 작업의 늦은 응답이 최신 결과를 덮어쓰지 않게 합니다. PG 조회의 `404`나 설정 오류는 실패 확정으로 사용하지 않습니다. 자동 복구는 이후 개선 후보로 남깁니다.

기술은 현재 프로젝트에 설정된 Java 21, Spring Boot, JPA, PostgreSQL, Flyway를 사용합니다. Controller는 요청·응답, Service는 업무 규칙, Repository는 DB 접근을 담당하고, PG 연동 코드는 토스페이먼츠 승인·조회를 담당합니다. 주문·결제 테이블과 제약조건은 Flyway 마이그레이션으로 관리합니다.

### 2.4. MVP를 만들고 확인하는 방법

구현 작업은 주문 저장·조회, 토스페이먼츠 결제창·PG 연동, 승인·결과 저장 등으로 작게 나눠 자주 실행하고 테스트합니다. **이 작업들은 모두 하나의 초기 MVP를 완성하기 위한 작업**입니다. 중간에 확인한 문제는 바로 반영하며, 주문부터 결제 결과 조회까지 연결된 흐름을 계속 확인합니다.

업무 규칙은 단위 테스트로, API·DB와 PG 응답 처리의 연결은 통합 테스트로 검증합니다. 다음은 MVP에서 확인할 주요 상황입니다.

| 상황 | 기대 결과 |
| --- | --- |
| 정상 주문·테스트 결제 | 10,000원 주문을 생성하고 PG 승인 결과를 저장하며, 화면과 재조회 결과가 일치합니다. |
| 주문 금액 변경 시도·승인 금액 불일치 | 서버가 정한 주문 금액을 유지하고, 일치하지 않는 승인 요청은 거부합니다. |
| 명확한 결제 거절 | 결제 완료로 기록하지 않고 고객이 실패를 알 수 있게 표시합니다. |
| 잘못된 요청·없는 주문 | 정해진 오류로 응답하고 잘못된 데이터를 저장하지 않습니다. |
| 중복·동시 승인 요청 | 같은 결제가 중복 처리되거나 기존 결과가 잘못 바뀌지 않습니다. |
| 응답 유실·PG 처리 후 DB 저장 실패 | 결과를 임의로 확정하지 않고, 보관한 정보로 PG 결과를 조회해 DB와 맞출 수 있습니다. |

[README의 로컬 실행 방법](../README.md#로컬-실행)에 따라 개발 중 동작을 확인하고, 접근을 제한한 테스트 환경에 MVP를 배포해 브라우저에서 사용해봅니다. 토스페이먼츠 테스트 키를 사용하며, 서버 시크릿 키와 DB 연결 정보는 환경변수로 관리합니다. 로그를 확인해 오류와 결과 확인이 필요한 결제를 점검합니다.

### 2.5. 초기 MVP의 완료 기준

**고객 역할로 주문 생성부터 테스트 결제와 결과 재조회까지 직접 진행하고, 판매자 역할로 저장된 결제 정보와 PG 결제 결과가 일치하는지 확인할 수 있어야 합니다.** 관련 테스트를 통과하고 테스트 환경에서의 동작 확인까지 마칩니다.

사용해본 뒤에는 결제 진행 중 막힌 지점, 결과를 이해하기 어려운 부분, 판매자가 정보를 확인할 때 불편한 점을 기록합니다. 이 관찰을 바탕으로 다음에 보완할 내용을 정합니다.

## 3. MVP 사용 후 필요한 내용을 보충합니다

MVP를 사용하며 발견한 문제와 추가 요구를 **백로그(할 일 목록)**에 모읍니다. 중요도가 높은 항목부터 작은 단위로 선택해 설계·구현·테스트하고, 다시 사용해본 결과로 다음 작업을 정합니다. 아래 항목은 개선 후보이며 순서는 피드백에 따라 정합니다.

| 발견한 필요 | 보충할 수 있는 내용 |
| --- | --- |
| 결제 결과를 이해하기 어렵다 | 결과 화면, 상태 설명, 오류 메시지 개선 |
| 결제한 주문을 취소하고 싶다 | 전액 취소 요청, PG 취소 결과 저장·조회 |
| 확인이 필요한 결제를 수동으로 찾기 어렵다 | PG 재조회와 DB 불일치 복구 자동화, 운영 화면 |
| 상품과 주문 조건이 늘어났다 | 상품 관리, 수량·할인, 부분 취소 |
| 배송이나 판매 대금 입금을 관리해야 한다 | 배송 연동, 정산 관리 |

예를 들어 전액 취소가 필요해지면 다음 도메인 규칙을 구체화합니다. 결제 전에는 주문을 취소하고, 결제 후에는 이미 받은 돈을 돌려주는 처리가 함께 필요합니다. **우리 DB의 주문 상태만 바꿔도 카드 결제가 취소되는 것은 아닙니다.** PG에 취소를 요청하고 결과를 확인해 저장해야 합니다.

PG 취소 후 고객 카드에 반영되기까지는 시간이 걸릴 수 있습니다. 취소 기능을 추가할 때 취소 가능 조건, 중복 요청, 통신 오류 처리와 고객 안내를 함께 정합니다. [토스 공식 취소 설명](https://docs.tosspayments.com/guides/v2/cancel-payment)

초기 MVP는 학습용 테스트 서비스입니다. 실제 고객에게 공개하려면 인증과 주문 접근 권한을 비롯한 운영 요구사항을 별도로 정하고 구현합니다.

이 문서는 한 파일로 유지합니다. 현재 MVP에 필요한 내용을 구체화하고, 이후에는 실제로 확인한 문제와 결정한 개선 사항을 추가합니다.

## 4. 현재 위치

현재 주문·결제 API, PostgreSQL/Flyway 저장 구조, 토스 테스트 결제창, 결제 결과 화면과 수동 재확인 기능을 구현했습니다. 단위 테스트와 실제 PostgreSQL 컨테이너 통합 테스트로 정상 처리·중복 요청·통신 오류·PG 승인 후 저장 실패·복구를 검증합니다. 자동 테스트의 PG 응답은 모의 응답이며, 실제 테스트 상점의 카드 인증과 배포 환경 검증은 별도로 남아 있습니다.
