# 결제 서비스 개발 계획과 기본 개념

## 1. 소프트웨어는 어떤 방식으로 개발하나요?

전 세계 소프트웨어 개발 현장에서 개발의 전체 과정을 설명할 때 널리 사용하는 개념이 **SDLC(Software Development Life Cycle, 소프트웨어 개발 생명주기)**입니다. 웹 서비스도 이 생명주기를 따라 기획하고, 만들고, 운영하며 개선합니다.

```text
기획 → 요구사항 정의 → 설계 → 구현 → 테스트 → 배포 → 운영·피드백 → 개선
```

SDLC는 전체 과정을 나타내는 큰 틀이며, **그 과정을 어떻게 진행하느냐에 따라 여러 개발 방식**이 있습니다. 대표적인 예는 다음과 같습니다. [AWS의 SDLC 설명](https://aws.amazon.com/ko/what-is/sdlc/)

| 방식 | 진행하는 방법 |
| --- | --- |
| 폭포수(Waterfall) | 요구사항과 설계 등 앞 단계를 마친 뒤 다음 단계로 순서대로 진행합니다. |
| 애자일(Agile) | 작은 기능을 만들어 확인하는 과정을 짧게 반복하고, 피드백에 따라 요구사항과 계획을 조정합니다. |

웹 서비스 개발에서도 애자일 방식을 많이 활용합니다. 사용자 반응을 확인하며 기능을 자주 추가하고 수정하는 서비스에 잘 맞기 때문입니다.

### 애자일 방식이란?

**작게 만들고, 직접 사용해보고, 배운 내용을 다음 개발에 반영하는 방식**입니다. 동작하는 소프트웨어를 자주 제공하고 사용자와 소통하며, 변화에 맞춰 계획을 조정하는 것을 중요하게 생각합니다. [애자일 원칙](https://agilemanifesto.org/iso/ko/principles.html)

이 프로젝트에서는 한 번의 반복을 다음 흐름으로 진행합니다.

```text
작은 기능 선택 → 요구사항·설계 → 구현·테스트 → 실행·배포 → 운영·피드백
      ↑                                                        │
      └────────────── 다음에 만들거나 개선할 기능 선택 ──────────┘
```

예를 들어 주문 생성·조회 기능을 먼저 완성하고 확인한 뒤, 결제와 취소 기능을 차례로 추가합니다. 각 반복 안에서 기획부터 피드백까지 진행하며, 구현 중 새로 알게 된 내용은 요구사항과 설계에 다시 반영합니다.

**우리 결제 서비스도 이 애자일 방식으로 개발합니다.** 아래는 프로젝트의 초기 방향을 정하고 첫 반복을 진행하는 순서입니다. 다음 반복에서도 같은 흐름으로 필요한 내용을 갱신합니다.

## 2. 기획: 누구의 어떤 문제를 해결할까요?

티셔츠 한 장을 **10,000원**에 파는 작은 쇼핑몰을 생각해봅시다. 고객은 카드로 결제하고 나중에 티셔츠를 배송받습니다.

고객은 “내 결제가 완료됐는지” 확인하고 싶고, 판매자는 “어떤 주문의 결제가 완료됐는지” 정확히 알아야 합니다. 그래서 **고객이 주문하고 결제한 뒤, 그 결과를 확인할 수 있는 서비스**를 만듭니다.

첫 목표는 다음 흐름이 연결되는 **MVP(최소 기능 제품)**입니다.

```text
티셔츠 1장 주문 → 토스페이먼츠 테스트 결제 → 서버 승인 → 결제 결과 조회
```

학습 범위는 상품 1종, 수량 1장, 금액 10,000원으로 고정하고 배송비와 할인은 제외합니다. 독립 결제 서비스 안에 예제용 최소 주문 기능을 함께 둡니다. 전액 취소는 MVP 다음에 추가하고, 상품 관리·배송 연동·부분 취소·정산 관리는 이후 필요에 따라 검토합니다.

## 3. 요구사항 분석: 결제 도메인과 업무 규칙을 이해합니다

요구사항을 정하려면 먼저 결제 업무가 어떻게 돌아가는지 알아야 합니다. 여기서 **도메인**은 “결제 업무에서 사용하는 개념과 규칙”이라는 뜻입니다. 아래 내용은 전체 흐름을 이해하기 위한 기초이며, 매 반복에서 구현할 기능의 규칙을 더 구체적으로 정합니다.

### 3.1. 토스페이먼츠는 어떤 역할을 하나요?

결제에는 다음 참여자가 있습니다.

| 참여자 | 하는 일 |
| --- | --- |
| 고객 | 상품을 고르고 카드로 결제합니다. |
| 우리 쇼핑몰 | 주문과 가격을 저장하고, 결제를 요청하고, 결과를 기록합니다. |
| 토스페이먼츠 | 쇼핑몰과 카드사 사이에서 결제 처리를 연결합니다. |
| 카드사 | 카드 사용자의 인증과 결제 승인 등을 처리합니다. |

이때 토스페이먼츠 같은 결제 대행사를 **PG**라고 부릅니다. 우리 쇼핑몰은 토스페이먼츠와 연동해서 카드 결제를 받을 수 있습니다. [토스 공식 설명](https://docs.tosspayments.com/resources/glossary/card-payment)

### 3.2. 주문부터 결제 완료까지

1. **고객이 주문합니다.** 우리 서버에 “티셔츠 1장, 10,000원, 결제 대기”로 저장합니다.
2. **결제 화면을 엽니다.** 고객이 결제하기 버튼을 누르면 토스페이먼츠의 결제 화면으로 진행합니다.
3. **고객이 카드 인증을 합니다.** 카드 앱에서 비밀번호 등을 입력합니다. 아직 우리 쇼핑몰의 결제 처리가 끝난 것은 아닙니다.
4. **우리 서버가 결제 승인을 요청합니다.** 저장된 주문과 결제금액이 맞는지 확인하고 토스페이먼츠에 승인을 요청합니다.
5. **승인 결과를 확인하고 저장합니다.** 결제가 성공한 것을 확인하면 해당 주문을 “결제 완료”로 기록하고 고객에게 보여줍니다.

**카드 인증을 마친 것과 결제가 최종 완료된 것은 구분해야 합니다.** 우리 서버가 승인 결과를 확인하는 단계까지 있어야 합니다. [토스 공식 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

### 3.3. 결제했다고 배송과 입금까지 끝난 건가요?

주문 하나에도 서로 다른 일이 진행됩니다.

| 개념 | 확인하려는 것 | 티셔츠 예시 |
| --- | --- | --- |
| 주문 | 무엇을 얼마에 구매했나요? | 티셔츠 1장, 10,000원 |
| 결제 | 고객의 결제가 완료됐나요? | 카드 결제 승인 완료 |
| 상품 제공 | 고객에게 상품을 전달했나요? | 티셔츠 배송 완료 |
| 정산 입금 | 판매대금이 사업자 계좌에 들어왔나요? | 수수료 등을 반영한 금액 입금 |

**결제 완료와 상품 제공 완료:** 월요일에 결제하고 수요일에 티셔츠를 받는다면, 월요일에는 결제만 완료된 상태입니다. 결제 후 배송에 문제가 생기면 “결제 완료, 배송 문제 발생”으로 기록하고 해결해야 합니다.

온라인 강의라면 배송 대신 이용권 발급이 상품 제공에 해당합니다. 결제는 성공했지만 이용권 발급이 실패할 수도 있습니다.

**결제 완료와 정산 입금:** 고객이 월요일에 카드로 결제해도, 사업자 계좌에는 계약에서 정한 정산 일정에 따라 대금이 들어옵니다. 결제금액에서 수수료 등이 반영되므로 고객이 결제한 금액과 사업자가 받는 금액도 다를 수 있습니다. [토스 공식 정산 설명](https://docs.tosspayments.com/resources/glossary/settlement)

이 구분은 설계에도 이어집니다. **결제 상태, 배송 상태, 정산 상태를 각각 관리**해야 한쪽의 문제를 다른 쪽의 실패로 잘못 처리하지 않습니다. 지금은 주문·결제만 구현하고, 배송·정산 기능을 추가할 때 별도의 상태를 설계합니다.

### 3.4. 고객이 취소하면 어떻게 하나요?

아직 티셔츠를 보내지 않았다고 가정해봅시다.

- **결제 전 취소:** 주문을 취소하면 됩니다. 받은 돈이 없으므로 돌려줄 돈도 없습니다.
- **결제 후 취소:** 주문 취소와 함께, 이미 결제한 10,000원을 돌려주는 처리가 필요합니다.

결제 후에는 우리 서버가 토스페이먼츠에 결제 취소를 요청하고 결과를 확인합니다. 우리 DB의 주문 상태만 “취소”로 바꾼다고 카드 결제까지 취소되는 것은 아닙니다.

PG에서 취소를 처리한 뒤에도 고객 카드에 반영되기까지는 시간이 걸릴 수 있습니다. [토스 공식 취소 설명](https://docs.tosspayments.com/guides/v2/cancel-payment)

## 4. 반복 계획: 이번에는 어떤 기능을 완성할까요?

만들 기능과 개선할 일을 우선순위대로 모은 목록을 **백로그(Backlog)**라고 합니다. 우리 프로젝트의 초기 백로그는 다음과 같습니다. 각 반복이 끝나면 피드백에 따라 순서와 범위를 조정합니다.

| 우선순위 | 기능 | 동작 확인 목표 |
| --- | --- | --- |
| 1 | 주문 생성·조회 | 10,000원 주문이 저장되고, 주문번호로 같은 내용을 조회할 수 있습니다. |
| 2 | 테스트 결제 | 주문부터 결제 승인·결과 조회까지 연결해 첫 MVP를 완성합니다. |
| 3 | 전액 취소 | PG 취소 결과를 확인해 저장하고, 고객이 취소 결과를 조회할 수 있습니다. |
| 4 | 결과 확인·복구 개선 | 통신 끊김이나 DB 저장 실패로 남은 불일치를 찾아 복구하는 작업을 자동화합니다. |

우선 **첫 반복의 목표를 ‘주문 생성·조회’**로 정합니다. 각 기능의 크기가 커지면 더 작은 반복으로 나눕니다.

사용자 요구는 “티셔츠 한 장을 주문하고, 주문번호로 주문 내용을 확인하고 싶다”입니다. 이를 확인 가능한 요구사항으로 바꾸면 다음과 같습니다.

1. 주문하면 서버가 주문번호를 생성하고 티셔츠 1장, 10,000원으로 저장합니다.
2. 가격은 서버가 결정합니다. 클라이언트가 보낸 금액으로 주문 가격이 바뀌지 않아야 합니다.
3. 주문번호로 상품명, 수량, 주문금액, 생성 시각을 조회할 수 있어야 합니다.
4. 잘못된 요청과 존재하지 않는 주문 조회는 정해진 오류로 응답해야 합니다.

## 5. 설계: 이번 기능을 어떻게 만들까요?

첫 반복의 요구사항을 바탕으로 사용자 흐름, API, 데이터와 코드 구조를 정합니다. 아래는 초기 설계안이며, 구현 전에 요청·응답 필드와 검증 조건을 구체화합니다.

### 5.1. 사용자 흐름과 화면

```text
주문 생성 요청 → 주문번호 확인 → 해당 주문 조회 → 주문 내용 확인
```

첫 반복에서는 API 호출로 이 흐름을 확인합니다. 테스트 결제를 추가하는 반복에서는 주문 화면, 결제 버튼, 성공·실패·확인 중인 결과를 보여줄 최소 화면을 설계합니다.

### 5.2. API와 데이터

| 항목 | 첫 반복의 설계 |
| --- | --- |
| 주문 생성 | `POST /orders`: 주문을 저장하고 주문번호와 주문 내용을 `201`로 응답합니다. |
| 주문 조회 | `GET /orders/{orderId}`: 저장된 주문 내용을 `200`으로 응답합니다. |
| 오류 | 잘못된 요청은 `400`, 존재하지 않는 주문은 `404`로 응답합니다. |
| 주문 데이터 | 주문번호, 상품명, 수량, 주문금액, 생성 시각을 저장합니다. 주문번호는 중복되지 않도록 DB 제약조건을 둡니다. |

결제 기능을 추가할 때 주문과 연결되는 결제 기록, PG 결제 식별자인 `paymentKey`, 결제 상태와 상태 변경 규칙을 설계합니다. 앞서 배운 “카드 인증과 최종 승인은 다르다”는 규칙은 **PG 승인 성공을 확인한 뒤에 결제 완료로 기록한다**는 설계로 이어집니다.

### 5.3. 기술과 코드 구조

현재 프로젝트에 설정된 Java 21, Spring Boot, JPA, PostgreSQL, Flyway를 사용합니다.

```text
Controller(요청·응답) → Service(업무 규칙) → Repository(DB 접근) → PostgreSQL
```

주문 엔티티로 저장할 데이터를 표현하고, Flyway 마이그레이션으로 DB 테이블과 제약조건을 생성합니다. 결제 반복에서는 Service가 PG 연동 코드를 통해 토스페이먼츠에 승인·조회 등을 요청하도록 확장합니다.

## 6. 구현: 설계한 기능을 실제 코드로 연결합니다

첫 반복에서는 다음 작업으로 주문 생성·조회 흐름을 완성합니다.

1. 주문 테이블 마이그레이션과 주문 엔티티를 만듭니다.
2. Repository와 Service에 주문 저장·조회, 서버 금액 결정 규칙을 구현합니다.
3. Controller에 주문 생성·조회 API와 요청 검증·오류 응답을 연결합니다.
4. API로 주문을 생성하고, 반환된 주문번호로 DB에 저장된 내용을 다시 조회합니다.

결제 반복에서는 최소 화면 → 토스 테스트 결제 → 서버 금액 검증·승인 → 결과 저장·조회까지 연결합니다. **금액 검증과 중복·동시 요청 제어는 첫 결제 구현부터 포함합니다.** 통신 시간 초과처럼 결과가 불명확하면 “확인 필요”로 남기고 PG 조회로 확인합니다. PG 승인 후 DB 저장에 실패해도 복구할 수 있도록 요청 식별 정보를 미리 보관합니다.

전액 취소 반복에서도 취소 가능 상태와 중복 요청을 검증하고, PG 취소 결과를 확인한 뒤 저장합니다. 이후 복구 개선 반복에서 결과 확인·복구 작업의 자동화를 보강합니다.

## 7. 테스트: 정한 요구사항대로 동작하나요?

구현하면서 업무 규칙을 검증하는 단위 테스트와 API·DB가 연결되는지 확인하는 통합 테스트를 작성합니다. 첫 반복에서는 다음을 확인합니다.

| 상황 | 기대 결과 |
| --- | --- |
| 정상 주문 생성 후 조회 | 생성은 `201`, 조회는 `200`이며 저장한 주문 내용과 응답이 일치합니다. |
| 클라이언트가 주문금액 변경을 시도 | 서버가 정한 10,000원이 유지되거나 요청이 거부됩니다. |
| 요청 형식이나 값이 잘못됨 | `400`으로 응답하고 잘못된 주문을 저장하지 않습니다. |
| 없는 주문번호로 조회 | `404`로 응답합니다. |

결제 반복에서는 성공·실패뿐 아니라 금액 불일치, 중복·동시 승인 요청, 응답 유실, PG 처리 후 DB 저장 실패를 확인합니다. 취소 반복에서는 전액 취소 성공, 취소 불가능한 상태, 중복 요청과 통신 오류를 확인합니다. 결과를 확인하지 못한 요청을 성공이나 실패로 잘못 확정하지 않는 것도 완료 기준입니다.

## 8. 실행·배포·운영: 실제 환경에서 확인합니다

첫 반복은 [README의 로컬 실행 방법](../README.md#로컬-실행)에 따라 PostgreSQL과 애플리케이션을 실행하고 API로 확인합니다. 첫 MVP부터는 접근을 제한한 테스트 환경에 배포해 브라우저에서 주문·결제·결과 조회를 직접 사용해봅니다. 이때 토스페이먼츠 테스트 키를 사용하고, 서버 시크릿 키와 DB 연결 정보는 환경변수로 관리합니다.

배포 후에는 주문·결제 결과가 정상적으로 조회되는지, 오류나 확인이 필요한 결제가 남는지 로그를 살펴봅니다. 발견한 문제는 재현 조건과 함께 백로그에 기록합니다.

현재 범위는 학습용 테스트 서비스입니다. 실제 고객에게 공개하는 단계에서는 로그인 등 인증 방식과 주문 접근 권한을 비롯한 운영 요구사항을 정하고 구현합니다.

## 9. 피드백·개선: 다음 반복을 정합니다

직접 사용해본 결과를 처음 정한 목표와 비교합니다. 초기에는 우리가 고객과 판매자 역할로 확인하고, 테스트 사용자가 생기면 그 의견도 반영합니다.

예를 들어 첫 반복에서 “주문은 조회되지만 주문번호를 응답에서 찾기 어렵다”면 응답을 개선합니다. 주문 흐름이 충분히 확인되면 다음 목표를 “이 주문에 대해 테스트 결제를 하고 결과를 조회하기”로 정합니다.

그다음 다시 **요구사항·도메인 규칙 확인 → 설계 → 구현·테스트 → 배포·운영 → 피드백**을 진행합니다. 각 반복은 완료 기준 충족, 관련 테스트 통과, 로컬 또는 테스트 환경에서의 동작 확인, 피드백과 문서 갱신까지 마칩니다.

이 문서는 한 파일로 유지합니다. 현재 반복의 설계는 구현 전에 구체화하고, 다음 기능은 목표 중심으로 관리합니다. 진행하면서 확정한 규칙과 변경 이유를 해당 항목에 반영합니다.
