# 온라인 결제 도메인 이해와 실무 기획

토스페이먼츠 PG를 이용하는 온라인 서비스의 결제 도메인 문서

- 작성·공식 자료 확인일: 2026-09-10
- 문서 상태: 도메인 학습 및 기획 초안
- 기본 사례: 국내 고객에게 원화로 상품을 판매하는 단일 판매자 쇼핑몰
- 독자: 결제 시스템을 처음 기획하거나 구현하려는 개발자·서비스 운영자

이 문서에서 **도메인**은 웹사이트 주소가 아니라, 사업에서 사용하는 개념·업무·규칙을 뜻한다. 결제 도메인을 이해한다는 것은 “고객이 무엇에 대해 얼마를 냈고, 무엇을 제공받아야 하며, 문제가 생기면 누가 어떤 근거로 처리하는가”를 설명할 수 있다는 뜻이다.

본문의 **공식 동작**에는 토스페이먼츠 공식 출처를 연결했다. **설계 제안·예시 정책**은 이 프로젝트를 위한 초안이며, PG가 강제하는 규칙이나 확정된 사업 정책이 아니다. 아직 업종이 정해지지 않았으므로 모든 사업을 한 번에 지원한다고 가정하지 않는다.

## 읽는 순서

1. 이 문서의 1~5장으로 결제의 개념과 업무 경계를 이해한다.
2. 6~10장으로 상태·금액·실패 상황을 이해한다.
3. 11~14장으로 운영과 첫 구현 범위를 정리한다.
4. [실무 시나리오](payment-scenarios.md)에서 실제 주문을 따라가 본다.
5. [기획 정책 결정표](payment-policy-decisions.md)에서 자신의 사업에 맞는 정책을 결정한다.

## 1. 결제 시스템이 해결해야 하는 문제

결제 버튼을 눌렀을 때 돈을 받는 것은 전체 업무의 일부다. 시스템은 다음 질문에 답할 수 있어야 한다.

| 질문 | 필요한 도메인 |
| --- | --- |
| 고객이 무엇을 어떤 가격에 구매했는가? | 주문·주문상품·가격 |
| 정말로 결제가 완료됐는가? | 결제·결제 시도·승인 |
| 상품을 보내거나 이용권을 발급해도 되는가? | 주문 확정·상품 제공 |
| 일부 상품만 취소하면 얼마를 돌려주는가? | 취소·반품·환불·할인 배분 |
| PG와 우리 기록이 다르면 어느 쪽이 누락됐는가? | 거래 기록·대사 |
| 고객이 낸 돈 중 사업자가 언제 얼마를 받는가? | 정산·수수료 |
| 누가 어떤 이유로 결제를 취소했는가? | 운영 권한·감사 이력 |

특히 네 가지 구분이 중요하다.

- **주문 생성과 결제 완료는 별개다.** 주문은 만들었지만 결제를 포기할 수 있다.
- **결제 인증과 결제 승인은 별개다.** 카드 인증 후에도 서버의 승인 처리가 남아 있다.
- **결제 완료와 상품 제공 완료는 별개다.** 돈을 받았지만 배송이나 이용권 발급이 실패할 수 있다.
- **결제 완료와 정산 입금은 별개다.** 고객 결제 후 사업자에게 대금이 지급되기까지 시간이 있다.

## 2. 누가 무엇을 담당하는가

| 참여자 | 담당 업무 | 쇼핑몰이 확인할 사항 |
| --- | --- | --- |
| 구매자 | 상품 선택, 결제 인증, 취소·반품 요청 | 주문의 당사자인가, 어떤 금액에 동의했는가 |
| 판매자·서비스 사업자 | 상품 판매, 공급, 환불 정책, 고객 응대 | 고객과 약속한 판매 조건을 이행했는가 |
| 쇼핑몰 시스템 | 주문 금액 확정, PG 연동, 결과 기록, 제공 지시 | 돈과 주문 상태가 서로 맞는가 |
| PG사: 토스페이먼츠 | 결제기관 연결, 결제 처리 인터페이스, 거래·정산 정보 제공 | 해당 상점 계약과 결제수단에서 가능한 처리는 무엇인가 |
| 카드사·은행 등 | 결제수단 인증, 승인·입출금 등 금융 처리 | 승인 거절·점검·입금 오류가 있는가 |
| 물류·서비스 제공 시스템 | 출고·배송, 콘텐츠 접근권·예약 제공 | 같은 주문을 중복 제공하지 않았는가 |
| CS·운영·재무 담당자 | 문의 처리, 환불 검토, 정산 확인, 장애 복구 | 어떤 증거로 판단하고 조치했는가 |

PG는 Payment Gateway의 약자다. 카드 결제에서는 PG가 VAN 등 결제망을 거쳐 카드사와 연결된다. VAN은 결제 정보를 중계하는 역할로 이해하면 된다. 첫 쇼핑몰 기획에서는 PG를 통해 연동되는 외부 결제망으로 묶어 생각해도 충분하다. [공식: 카드 결제의 참여자와 처리 과정](https://docs.tosspayments.com/resources/glossary/card-payment)

**토스페이먼츠와 토스페이는 구분한다.** 토스페이먼츠는 여기서 연동할 PG사이고, 토스페이는 고객이 선택할 수 있는 간편결제 수단 중 하나다. 토스페이먼츠를 연동한다고 고객이 반드시 토스페이로만 결제하는 것은 아니다. [공식: 결제수단 정책](https://docs.tosspayments.com/guides/v2/get-started/payment-methods)

## 3. 상품 구매 한 건을 끝까지 따라가기

고객이 티셔츠 30,000원, 모자 20,000원을 구매하고 배송비 3,000원을 내는 상황을 생각해 보자. 할인은 없고 총 결제금액은 **53,000원**이다.

| 단계 | 일어나는 일 | 반드시 남길 사실 |
| --- | --- | --- |
| 1. 주문 준비 | 판매 가능 여부와 최종 가격 확인 | 상품·수량·단가·배송비·구매자 |
| 2. 주문 생성 | 53,000원을 지불할 주문 생성 | 주문번호와 당시 판매 조건 |
| 3. 결제 시도 | 고객이 결제수단을 선택하고 인증 | 어느 주문의 몇 번째 시도인지 |
| 4. 결제 승인 | 서버가 주문과 금액을 검증하고 PG 승인 요청 | PG 결제 식별자와 승인 결과 |
| 5. 주문 확정 | 검증된 결제 결과로 판매를 확정 | 확정 시각, 제공할 상품·수량 |
| 6. 상품 제공 | 상품 출고·배송 | 출고·배송 이력 |
| 7. 취소·반품 | 고객 요청과 판매 조건 검토 | 대상 상품·수량·사유·판정 |
| 8. 환불 처리 | 확정된 금액을 원래 결제수단으로 반환 처리 | 환불 요청과 PG 취소 거래 |
| 9. 정산 확인 | PG 계산 내역과 실제 사업자 입금 확인 | 수수료·정산일·입금 차이 |

결제에 실패했다고 주문 내역까지 없애면, 고객의 재시도와 문의를 설명하기 어렵다. 반대로 결제에 성공했다고 배송까지 성공한 것으로 기록하면 미배송 사고를 찾기 어렵다. 각 업무의 사실을 따로 남기는 이유다.

## 4. 자주 쓰는 용어

| 용어 | 의미 | 혼동하기 쉬운 점 |
| --- | --- | --- |
| 주문, Order | 고객이 어떤 조건으로 무엇을 구매하는지에 대한 기록 | 결제 전에도 존재한다 |
| 주문상품, Order Line | 주문 안의 상품·옵션·수량·가격 단위 | 부분 취소·부분 배송의 기준이다 |
| 결제, Payment | 주문 대금을 PG로 수납하는 업무 기록 | 상품 배송 상태를 포함하지 않는다 |
| 결제 시도, Payment Attempt | 고객이 결제를 진행한 개별 시도 | 실패 후 다른 카드로 다시 시도할 수 있다 |
| 인증 | 결제수단의 사용자를 확인하는 과정 | 인증 성공만으로 구매 확정하지 않는다 |
| 승인 | 인증한 결제를 결제기관이 받아들인 결과 | 사업자 계좌로 입금됐다는 뜻은 아니다 |
| 매입 | 승인된 카드 거래를 대금 청구·정산 과정에 넘기는 단계 | 쇼핑몰의 상품 매입과 다른 용어다 |
| 거래, Transaction | 승인·취소 등 돈의 변화를 남기는 개별 기록 | 한 결제에 여러 취소 거래가 생길 수 있다 |
| 주문 취소 | 상품을 제공하기 전 구매 약속을 철회하는 업무 | 아직 미결제라면 반환할 돈이 없다 |
| 반품 | 제공된 실물 상품을 돌려받는 업무 | 반품 신청 즉시 환불되는 것은 아니다 |
| 환불 | 고객에게 반환할 대금을 처리하는 업무 | PG 취소 처리와 고객의 실제 반영 시점은 다를 수 있다 |
| 정산 | 사업자에게 지급할 대금과 지급일을 계산·처리하는 업무 | 고객 환불이나 판매자 간 배분과 구분한다 |
| 대사, Reconciliation | 서로 다른 기록을 비교해 차이를 찾고 해소하는 업무 | 조회만 하고 차이를 방치하면 해결되지 않는다 |
| 웹훅, Webhook | PG가 우리 서버로 상태 변화를 알리는 방식 | 중복·지연·누락에 대비해야 한다 |
| 멱등성, Idempotency | 같은 업무 요청을 반복해도 금전 효과가 한 번만 생기는 성질 | 버튼 비활성화만으로 보장되지 않는다 |

인증·승인·매입의 금융 처리 의미는 [공식 카드 결제 설명](https://docs.tosspayments.com/resources/glossary/card-payment)을, 취소 후 반환 시점의 차이는 [공식 결제 취소 안내](https://docs.tosspayments.com/guides/v2/cancel-payment)를 참고한다. 나머지는 이 문서에서 사용할 업무 용어의 정의다.

## 5. 업무 경계와 핵심 개념

### 5.1 결제 서비스가 소유할 것

| 영역 | 책임 | 결제 영역과 주고받을 정보 |
| --- | --- | --- |
| 상품·가격 | 판매 여부, 가격, 과세 구분 | 구매 시점의 확정 가격·상품 설명 |
| 주문 | 구매 내역, 주문 금액, 취소할 상품·수량 | 주문 식별자, 청구금액, 환불 근거 |
| 결제 | 승인·조회·취소 요청, PG 결과, 거래 이력 | 검증된 수납·취소 결과 |
| 재고·예약 | 한정 수량·좌석의 확보와 해제 | 확보 가능 여부, 확보 만료 시각 |
| 배송·이용권 | 고객에게 실제 상품·권리 제공 | 제공 시작·완료·실패 결과 |
| 쿠폰·포인트 | 할인 자격, 사용·복원 이력 | 주문별 사용량·복원량 |
| 정산·재무 | 수수료·지급·입금·대사 관리 | 결제와 취소의 금액·시점 |

결제 서비스는 “티셔츠가 불량이므로 배송비까지 반환해야 한다”를 혼자 판단하지 않는다. 주문·반품 정책이 반환 금액을 결정하고, 결제 서비스는 그 요청의 권한과 잔액을 검증한 후 금전 처리를 담당한다.

여기서 경계는 **업무 책임의 구분**이다. 처음부터 각각을 별도 서버로 나눌 필요는 없다. 현재 저장소의 독립 결제 서비스도 향후 주문 시스템과 어떤 사실을 교환할지 먼저 정하면 된다.

### 5.2 데이터베이스보다 먼저 이해할 개념 모델

| 개념 | 남겨야 할 핵심 정보 | 필요한 이유 |
| --- | --- | --- |
| 주문 | 구매자, 통화, 확정 금액, 판매 조건, 상태 | 무엇을 얼마에 팔았는지 재현 |
| 주문상품 | 당시 상품명·옵션·단가·수량·할인 배분 | 상품 정보 변경 후에도 환불 금액 재현 |
| 결제 의무 | 주문에서 PG로 받아야 할 금액 | 재시도를 하나의 수납 목적에 연결 |
| 결제 시도 | 시도 식별자, PG 주문번호, 예상 금액, 결과 | 실패·재시도·중복 승인 추적 |
| PG 거래 | 승인·취소의 종류, 금액, 외부 식별자, 발생 시각 | 금액 변화의 근거 |
| 취소·환불 요청 | 대상 상품, 사유, 금액, 요청자, 진행 상태 | 고객 요청과 금융 결과 구분 |
| 정산 항목 | 연결 거래, 수수료, 지급 예정·확인 내역 | 수납부터 입금까지 추적 |
| 운영 사건 | 불일치 유형, 증거, 담당자, 조치, 종료 근거 | 장애와 수동 처리의 책임 추적 |

**제안하는 관계**는 주문 1건에 결제 의무 1건, 결제 의무에 결제 시도 여러 건이다. 결제 시도에는 아직 PG 거래가 없을 수도 있다. 승인된 시도에는 승인 거래와 여러 취소 거래가 연결될 수 있다. 환불 요청과 실제 취소 거래도 구분해 연결한다.

첫 범위는 주문 1건을 PG 결제 1건으로 전액 수납한다. 다른 결제수단으로 바꾸는 것은 새 시도이고, **응답을 못 받아 같은 승인을 다시 확인하는 것은 기존 시도의 재처리**다. 앞선 시도의 결과가 불확실할 때는 새 시도를 허용하지 않는 정책을 제안한다.

### 5.3 식별자를 구분하는 이유

| 식별자 | 발급 주체 | 역할 |
| --- | --- | --- |
| 내부 주문번호 | 우리 서비스 | 구매 내역 식별 |
| 내부 결제 시도 번호 | 우리 서비스 | 개별 시도 식별 |
| 토스 `orderId` | 우리 서비스 | PG 결제 요청 식별 |
| 토스 `paymentKey` | 토스페이먼츠 | 결제 조회·승인·취소 대상 식별 |
| 토스 `transactionKey` | 토스페이먼츠 | 승인·취소 거래 식별 |
| 내부 환불 요청 번호 | 우리 서비스 | 동일 환불 업무의 중복 방지 |
| 멱등키 | 우리 서비스 | 같은 PG 변경 요청의 재시도 식별 |

토스 식별자의 정의는 [공식 코어 API](https://docs.tosspayments.com/reference)에 따른다. 내부 이름과 관계는 설계 제안이다. 토스 `orderId`를 내부 주문번호와 반드시 같게 만들 필요는 없다. **새 결제 시도마다 새로운 PG 주문번호를 연결하고, 동일 시도의 통신 재시도에서는 기존 번호와 멱등키를 유지**하는 방식을 제안한다.

첫 범위에서는 전액 환불한 주문의 재구매도 새 주문으로 처리한다. 주문번호를 재활용하면 과거의 환불과 새 결제를 구분하기 어렵다.

## 6. 상태를 하나의 값으로 합치면 안 되는 이유

### 6.1 고객 화면에도 여러 상태가 공존한다

예를 들어 같은 주문에 **주문 확정 / 결제 완료 / 배송 준비 / 환불 요청 없음 / 정산 대기**가 동시에 존재한다. 이후 모자만 반품하면 **티셔츠 배송 완료 / 모자 반품 완료 / 결제 부분 취소**가 될 수 있다.

다음은 내부 업무 상태의 제안이다. 영문 명칭을 확정한 enum이나 DB 설계로 해석하지 않는다.

| 상태 축 | 예시 상태 | 판단 기준 |
| --- | --- | --- |
| 주문 | 결제 대기 → 주문 확정 → 거래 완료, 또는 취소 | 판매 약속의 진행 상황 |
| 상품 제공 | 미시작 → 준비 → 제공 중 → 제공 완료, 또는 제공 실패 | 출고·배송·권리 발급의 결과 |
| 결제 시도 | 준비 → 처리 중 → 입금 대기/수납 완료/실패/만료/중단 | 검증된 금융 처리 결과 |
| 승인 후 결제 | 수납 완료 → 부분 취소 → 전액 취소 | 승인금액과 취소 거래의 누계 |
| 환불 요청 | 접수 → 검토 → 실행 중 → PG 처리 완료, 또는 거절/실행 실패 | 환불 업무와 PG 처리 결과 |
| 확인 상태 | 확인됨 / 결과 확인 필요 / 운영 검토 필요 | 현재 결과를 얼마나 확실히 아는가 |
| 정산 | 지급 예정 / 지급 확인 / 차이 조사 중 | 정산 자료와 은행 입금 근거 |

결제 시도의 “중단”은 승인 요청이 없고 더 진행하지 않는 것이 확인된 경우다. 브라우저를 닫았다는 관측만으로 이미 처리 중인 결제를 중단·실패로 확정하지 않는다.

### 6.2 토스페이먼츠의 결제 상태

다음 값은 내부 주문 상태와 별도로 보존할 **PG 상태**다. [공식: Payment 상태 정의](https://docs.tosspayments.com/reference)

| 토스 상태 | 도메인에서 읽는 의미 |
| --- | --- |
| `READY` | 인증 전 준비 상태 |
| `IN_PROGRESS` | 인증을 마쳤고 승인 전인 상태 |
| `WAITING_FOR_DEPOSIT` | 가상계좌 입금 대기 |
| `DONE` | 결제 완료 |
| `PARTIAL_CANCELED` | 일부 금액 취소 |
| `CANCELED` | 전액 취소 또는 가상계좌 입금 전 취소 |
| `ABORTED` | 결제 승인 실패 |
| `EXPIRED` | 결제 유효시간 만료 |

### 6.3 상태를 바꾸는 데 필요한 근거

| 변경 | 필요한 근거 | 근거로 부족한 것 |
| --- | --- | --- |
| 주문을 확정 | 해당 주문·금액의 결제 완료 확인과 상품 확보 | 성공 페이지 방문 |
| 입금 대기를 완료로 변경 | PG 재조회로 실제 입금 상태 확인 | 계좌번호 발급 |
| 결제 실패 확정 | PG의 확정 결과 또는 승인 미발생이 확인된 종료 | 네트워크 시간 초과 |
| 환불을 PG 처리 완료로 변경 | 해당 환불과 연결된 취소 거래 확인 | 환불 버튼 클릭 |
| 정산 지급 확인 | 정산 내역과 실제 입금의 연결 | 결제 승인 알림 |

오래된 알림으로 최신 상태를 덮어쓰지 않는다. 다만 모든 상태가 한 방향으로만 움직인다고 가정해서도 안 된다. 가상계좌에는 **입금 오류로 완료 후 다시 입금 대기가 되는 경우**가 있다. 이런 변경은 PG 재조회로 확인하고, 이미 출고됐다면 별도 운영 사건으로 처리한다. [공식: 가상계좌 상태 변경 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events)

## 7. 정상 결제 흐름과 결과가 불확실한 흐름

### 7.1 카드·간편결제의 기본 흐름

공식 흐름은 결제 요청 → 구매자 인증 → 서버 승인이다. `successUrl` 도착은 최종 완료가 아니며, 주문번호·금액을 검증한 뒤 승인이 필요하다. 인증 유효시간은 현재 공식 안내상 10분이다. 이 시간과 상점의 주문 유효시간은 서로 다른 정책이다. [공식: 결제 흐름 이해하기](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

우리 서비스의 업무는 다음 순서로 설계한다.

1. 서버가 가격·배송비·할인을 계산하고 고객에게 최종 금액을 보여준다.
2. 고객이 동의한 주문 조건과 결제 시도를 저장한다.
3. 고객이 토스 결제 화면에서 결제수단을 인증한다.
4. 서버가 주문 소유권, 결제 시도, 확정 금액, 유효시간, 기존 수납 여부, 상품 확보를 확인한다.
5. 승인 요청 사실을 남기고 PG에 승인을 요청한다.
6. 검증된 결과를 저장하고, 해당 주문을 한 번만 확정한다.
7. 주문 확정에 따라 출고·이용권 발급을 시작한다. 실패 시 재처리할 작업도 남긴다.

클라이언트가 보낸 금액을 그대로 믿으면 고객이 가격을 변조할 수 있다. 승인 기준은 **서버에 저장한 주문 금액**이어야 한다. [공식: 서버 금액 검증 원칙](https://docs.tosspayments.com/guides/v2/get-started/llms-quick-reference)

### 7.2 가상계좌는 입금까지 기다려야 한다

가상계좌는 결제 절차 후 계좌를 발급받아도 아직 수납되지 않을 수 있다. 계좌 발급 후 입금 대기를 안내하고, 입금 알림과 PG 조회로 완료를 확인한다. [공식: 가상계좌 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/llms-quick-reference)

상점에는 별도 정책이 필요하다. 계좌 유효기간 동안 재고를 확보할지, 입금 전에 취소할지, 주문 만료와 입금이 거의 동시에 일어나면 어떻게 처리할지를 정한다. 이미 입금된 주문을 재고 만료만 보고 삭제해서는 안 된다.

### 7.3 “실패했다”와 “결과를 모른다”는 다르다

승인 요청 직후 통신이 끊겼다면 PG에서는 승인했는데 응답만 잃었을 수 있다. 따라서 **결과 확인 필요**로 표시하고 기존 결제를 조회한다. 새로운 결제 유도는 기존 시도의 수납 여부를 확인한 뒤에 한다.

| 확인 결과 | 제안하는 처리 |
| --- | --- |
| PG에서 완료, 내부 기록 누락 | 금액·주문 연결을 검증하고 내부 결과 복구 |
| PG에서 처리 중 | 확인 작업 유지, 고객에게 확인 중 안내 |
| PG에서 확정 실패·만료 | 시도 종료 후 재결제 경로 제공 |
| PG 조회도 실패하거나 잠시 조회되지 않음 | 즉시 미결제로 단정하지 않고 재확인·운영 이관 |
| 내부는 완료, PG 결과가 다름 | 제공 보류 가능 여부 확인 후 차이 조사 |

우리 DB 처리와 외부 PG 처리가 하나의 원자적 작업으로 성공한다고 가정할 수 없다. “PG 성공 → 내부 저장 실패”를 나중에 복구할 식별자와 요청 이력이 반드시 필요하다.

### 7.4 결제수단을 추가하면 운영 업무도 늘어난다

| 결제수단 | 이해할 특징 | 상점이 준비할 업무 |
| --- | --- | --- |
| 카드 | 인증·승인과 이후 취소 반영이 구분됨 | 승인 거절 안내, 취소 내역 조회 |
| 간편결제 | 고객이 등록한 카드·머니 등의 수단을 이용 | 서비스·실제 결제 구성별 취소 제약 확인 |
| 계좌이체 | 결제 과정에서 고객 계좌의 이체를 처리 | 은행 점검·이체 실패·증빙 안내 |
| 가상계좌 | 계좌 발급 뒤 고객이 별도로 입금 | 입금 기한·미입금·환불계좌 관리 |
| 휴대폰 | 통신사 소액결제 정책의 영향을 받음 | 한도·취소 가능 기간과 예외 대응 |

결제수단마다 지원 조건과 취소 제약이 다르다. 첫 범위에서는 필요한 수단부터 선택하고, 추가할 때 입금·환불·고객 안내 시나리오도 함께 검토한다. [공식: 결제수단 정책](https://docs.tosspayments.com/guides/v2/get-started/payment-methods)

## 8. 금액은 어떻게 관리하는가

### 8.1 주문 금액의 구성

학습용 기본식은 다음과 같다.

> PG 청구금액 = 상품 금액 합계 + 배송비 − 상점 할인 − 사용 포인트

이 식의 포인트는 **상점의 무상 적립 포인트를 사용하는 확장 예시**다. 선불 충전금·기프트카드·외부 간편결제사의 포인트는 별도 정책과 계약을 검토해야 한다. 특히 고객의 간편결제 앱 내부 결제 구성은 쇼핑몰 자체 포인트 장부와 다르다.

금액 관리의 설계 원칙은 다음과 같다.

- 국내 원화 금액은 원 단위 정수와 통화로 표현한다.
- 현재 상품 가격과 주문 당시 가격을 따로 남긴다.
- 결제 진행 중 가격을 조용히 바꾸지 않는다. 변경이 필요하면 기존 시도를 안전하게 종료하고 고객에게 다시 동의를 받는다.
- 할인·배송비·과세 구분은 주문상품과 연결해 저장한다.
- 부분 취소를 지원하려면 주문 시점에 할인과 포인트의 상품별 배분 규칙을 정한다.
- 최초 승인금액, 누적 취소금액, 남은 결제금액을 구분한다.
- 0원 주문은 PG에 승인할 돈이 없는 별도 주문 완료 흐름으로 기획한다. 첫 범위에서는 지원하지 않는 안을 제안한다.

### 8.2 환불 금액의 경계

단일 PG 수납을 기준으로 **신규 취소 가능액 = 최초 수납액 − 완료된 취소액 − 진행 중인 환불에 확보한 금액**으로 관리한다. 처리 결과가 불확실한 환불도 확보 금액을 유지한다. 실패가 확정된 경우에만 그 금액을 해제한다.

예를 들어 53,000원을 받고 20,000원을 환불 처리 중이면, 다른 운영자가 추가로 53,000원을 환불하도록 허용하지 않는다. 이 내부 계산은 중복 요청 방지용이며, PG 최신 잔액과 차이가 있으면 확인 후 처리한다.

토스의 `totalAmount`는 최초 금액, `balanceAmount`는 취소 후 잔액이다. 과거 승인금액을 환불 후 잔액으로 덮어쓰지 않는다. [공식: Payment 금액 필드](https://docs.tosspayments.com/reference)

부분 환불 계산은 [실무 시나리오의 할인·포인트 예제](payment-scenarios.md#3-할인과-포인트가-있는-부분-환불확장-예제)에서 다룬다.

### 8.3 세금·증빙도 금액의 일부다

과세·면세가 섞인 상품은 전체 금액만으로 충분하지 않다. 복합 과세 결제와 취소에서는 면세 금액도 정확히 전달해야 한다. 상품 세금과 PG 수수료에 대한 세금은 서로 다른 항목이다. [공식: 세금 처리](https://docs.tosspayments.com/guides/v2/learn/tax)

실제 업종이 정해지면 영수증 제공 방식, 현금영수증 처리, 과세 구분, 보관 항목을 기획한다. 결제금액이나 정산 입금액을 그대로 회계상 매출·이익으로 정의하지 않는다.

## 9. 취소·반품·환불은 어떻게 이어지는가

### 9.1 고객 요청에서 금융 처리까지

1. 고객 또는 운영자가 취소·반품을 요청한다.
2. 주문 주체, 대상 상품·수량, 제공 상태, 사유를 확인한다.
3. 출고를 막거나 반품 회수·검수를 진행한다.
4. 판매 정책에 따라 상품 대금·배송비·할인·포인트를 나눠 반환액을 확정한다.
5. 환불 요청 번호를 만들고 해당 금액을 다른 환불에서 쓰지 못하게 확보한다.
6. PG 취소를 실행하고 그 결과를 확인한다.
7. 취소 거래를 연결하고 쿠폰·포인트·재고 후속 처리를 진행한다.
8. 고객에게 PG 처리 결과와 결제수단별 반영 안내를 제공한다.

**환불 요청 접수, PG 취소 처리 완료, 고객 계좌·카드 반영은 서로 다른 사실**이다. PG에서 취소 완료를 확인해도 실제 고객 반영 시점까지 우리 시스템이 확인할 수 있는 것은 아니다. 확인 근거가 없으면 “고객 입금 완료” 상태를 임의로 만들지 않는다.

토스에서는 승인된 결제의 전체 또는 일부 금액 반환에 결제 취소 기능을 사용한다. 가상계좌는 입금 전 부분 취소가 불가능하고, 입금 후 반환에는 환불계좌 정보가 필요하다. 정산 후 취소는 이후 정산금과 상계될 수 있다. 세부 가능 기간·반영 시간은 수단과 상점 조건을 확인한다. [공식: 결제 취소하기](https://docs.tosspayments.com/guides/v2/cancel-payment)

### 9.2 자주 놓치는 정책

| 상황 | 먼저 정해야 할 정책 |
| --- | --- |
| 고객이 결제창만 닫음 | 미결제 시도 종료와 주문 유지 기간 |
| 결제 후 출고 전 취소 | 출고 작업과 취소 중 어느 쪽이 먼저 확정됐는지 |
| 출고 후 취소 요청 | 배송 중지 가능 여부와 반품 절차 |
| 일부 수량만 반품 | 수량별 할인 배분과 반환 금액 |
| 무료배송 조건 미달 | 최초 배송비를 다시 부담시키는지, 고객에게 어떻게 고지할지 |
| 판매자 귀책 반품 | 배송비 부담과 쿠폰 복원 기준 |
| PG 취소 실패 | 실패 사유 해결, 재처리, 수동 대응 책임자 |
| PG 취소 성공 후 내부 처리 실패 | 같은 취소 거래로 복구하고 중복 반환 방지 |

이미 취소 처리된 거래를 다시 PG로 취소하거나, PG 처리가 불확실한 동안 별도 계좌로 송금하면 이중 환불이 발생할 수 있다. 수동 환불은 원래 처리의 상태를 확인하고 별도 증거와 승인 이력을 남기는 운영 절차가 필요하다.

## 10. 중복·지연·장애에 대한 업무 규칙

### 10.1 멱등성은 동일한 업무를 식별하는 일이다

동일 환불 요청을 세 번 전송해도 한 번만 반환되어야 한다. 이를 위해 고객 요청, 내부 처리, PG 요청에 같은 업무의 식별 관계를 유지한다. 같은 금액이라도 고객이 나중에 별도로 요청한 두 번째 부분 환불은 새로운 업무다.

토스는 POST 요청에 멱등키를 지원하며, 키 유효기간은 최초 요청 기준 15일로 안내한다. PG의 키 보관 기간이 내부 중복 방지 기록의 보관 기간을 대신하지 않는다. [공식: 인증 및 기타 헤더 설정](https://docs.tosspayments.com/reference/using-api/authorization)

재시도는 같은 요청 내용과 키로 한다. 결과를 모르는 상태에서 키만 바꾸어 새 작업처럼 보내지 않는다. 수납 성공 횟수 제한, 환불 잔액 확보, 제공 작업의 중복 방지도 함께 필요하다.

### 10.2 웹훅은 확인을 시작하는 신호다

토스는 웹훅 응답을 10초 안에 200으로 받을 것을 안내하며 실패 시 재전송한다. 따라서 중복 수신은 정상적으로 다뤄야 한다. [공식: 웹훅 연결과 재전송](https://docs.tosspayments.com/guides/v2/webhook)

우리 설계에서는 수신 내용을 복구 가능하게 기록한 뒤 응답하고, 저장된 알림으로 결제를 조회·검증한다. PG 결제와 내부 주문의 연결·금액·상점·환경이 맞는지 확인한 후 상태를 반영한다. 처리 전 장애가 나도 저장된 알림을 재처리할 수 있어야 한다.

일반 결제 웹훅에 지급대행용 서명 검증을 그대로 적용하면 안 된다. 가상계좌 알림은 저장된 `secret` 검증을 사용하고, 결제 조회로 실제 상태를 확인한다. 또한 `CANCEL_STATUS_CHANGED`는 일반 국내 결제에 발송되지 않으므로 국내 취소 완료를 그 알림만 기다리는 구조로 만들지 않는다. [공식: 이벤트별 본문과 검증 범위](https://docs.tosspayments.com/reference/using-api/webhook-events)

중복 알림은 같은 거래를 두 번 반영하지 않는다. 늦게 도착한 알림은 PG 현재 상태와 거래 이력으로 판단한다. 웹훅만으로 복구가 완결된다고 가정하지 않고, 결과 확인 필요 건의 주기적 조회와 거래 대사를 함께 둔다.

### 10.3 지켜야 할 도메인 규칙

1. 주문 소유자 또는 권한 있는 운영자만 관련 작업을 요청한다.
2. 고객이 동의한 서버 확정 금액으로 승인한다.
3. 첫 범위에서 한 주문을 성공적으로 수납하는 시도는 하나다.
4. 승인·취소 결과가 불확실한 동안 경쟁하는 금전 요청을 막는다.
5. 반환 완료액과 진행 중 환불 확보액의 합은 수납액을 초과하지 않는다.
6. 결제 완료만으로 제공이 완료됐다고 기록하지 않는다.
7. 중복 이벤트가 와도 재고·포인트·이용권을 두 번 처리하지 않는다.
8. 승인과 취소의 과거 기록을 삭제하지 않고 정정 근거를 추가한다.
9. 운영자가 상태를 바꾸면 변경 전후·이유·증거·담당자가 남는다.
10. 오래 남은 확인 필요 건에는 담당자와 다음 확인 시각이 있다.

## 11. 정산과 대사는 운영의 일상 업무다

### 11.1 결제금액과 사업자 입금액

정산은 계약에 정해진 수수료와 지급 주기를 적용해 진행된다. 영업일·정산 기준일을 고려해야 하므로 “결제일에 며칠 더하기”로 모든 상점의 입금일을 확정할 수 없다. [공식: 정산](https://docs.tosspayments.com/resources/glossary/settlement)

**가상의 계산 예시**로, 고객 결제 53,000원에서 해당 거래의 수수료와 관련 세금 합계가 1,749원이라면 다른 조정이 없을 때 지급 예상액은 51,251원이다. 1,749원은 학습용 임의 값이며 토스의 실제 요율이 아니다.

승인과 취소가 서로 다른 정산 기간에 반영될 수 있고, 보류·조정 항목도 있을 수 있다. 예상액만으로 지급 완료를 표시하지 않고 실제 정산 자료와 입금 증거를 연결한다.

### 11.2 세 가지 대사

| 비교 대상 | 찾으려는 문제 | 결과물 |
| --- | --- | --- |
| 내부 결제·취소 ↔ PG 거래 | 누락, 중복, 금액·상태 차이 | 거래 차이 목록과 복구 이력 |
| PG 거래 ↔ PG 정산 자료 | 정산 대상 누락, 수수료·조정 차이 | 정산 차이 목록과 확인 결과 |
| PG 지급 내역 ↔ 사업자 계좌 | 지급 누락, 묶음 입금, 실제 입금 차이 | 입금 연결과 미확인 목록 |

이는 이 프로젝트에 제안하는 운영 구조다. 거래 식별자, 상점, 통화, 금액, 승인·취소 시점을 기준으로 비교하고 자정 경계·지연 반영을 고려해 최근 구간을 겹쳐 확인한다. PG에만 존재하는 거래도 찾을 수 있도록 내부 결제 목록만 순회하는 방식에 한정하지 않는다.

### 11.3 운영자가 볼 화면과 지표

| 화면·지표 | 있어야 하는 이유 |
| --- | --- |
| 주문별 결제 타임라인 | 고객 문의 한 건의 전체 경과 확인 |
| 결제 시도·PG 거래 검색 | 다른 카드 재시도와 중복 결제 조사 |
| 환불 검토·진행 목록 | 환불 잔액·실패 사유·계류 시간 확인 |
| 결과 확인 필요 목록 | 응답 유실 건의 방치 방지 |
| 정산·입금 차이 목록 | 실제 들어온 대금 확인 |
| 운영 변경 이력 | 누가 무엇을 처리했는지 추적 |
| 승인 성공률 | 결제수단·PG 응답별 품질 확인 |
| 장기 미확인·환불 실패 건수 | 자동 복구가 해결하지 못한 문제 발견 |

승인 성공률은 “승인 성공 시도 / 승인 요청 시도”처럼 분모를 명시한다. 결제창 진입 후 이탈률과 섞으면 금융 장애와 구매 포기를 구분하기 어렵다. 첫 운영 기준으로 일 1회 대사, 미확인 건의 수시 확인을 제안하며 구체적인 간격은 정책표에서 정한다.

## 12. 고객 경험·권한·출시 준비

### 12.1 고객에게 필요한 안내

| 상황 | 화면에서 전달할 내용 |
| --- | --- |
| 결제 전 | 상품·수량·할인·배송비·총액·취소 조건 |
| 결제 확인 중 | “결제 결과를 확인하고 있습니다.”와 주문 조회 경로 |
| 결제 거절 | 고객이 해결할 수 있는 안내와 재시도 경로 |
| 가상계좌 입금 대기 | 은행·계좌·금액·입금 기한·미입금 시 처리 |
| 결제 완료 | 주문번호·수납금액·제공 예정·영수증 경로 |
| 환불 접수 | 반환 대상·예상 금액·추가 확인사항 |
| PG 취소 처리 완료 | 처리 금액·처리일·결제수단별 반영 안내 |

고객에게 내부 오류 코드만 보여주거나, 결과가 불확실한데 “다시 결제하세요”라고 바로 안내하지 않는다.

### 12.2 운영 권한과 기록

조회 담당, 환불 실행 담당, 예외 처리 승인 담당의 권한을 구분한다. 환불 사유와 금액을 확인할 수 있는 화면에서 실행하고, 계좌정보·개인정보는 필요한 사람에게 필요한 범위로만 제공한다. 비회원 주문 조회에는 주문번호 외에 소유권을 확인하는 수단이 필요하다.

시크릿 키는 서버에서만 관리한다. 키·카드 인증정보·환불계좌 전체를 일반 로그에 남기지 않고, 거래 추적에 필요한 식별자와 마스킹된 정보를 사용한다. [공식: API 키 사용 원칙](https://docs.tosspayments.com/guides/v2/get-started/llms-quick-reference)

### 12.3 실제 판매 전 확인할 항목

테스트 연동과 라이브 판매 개시는 별개다. 계약·홈페이지 검수·결제수단 심사를 거쳐 실제 사용 가능한 수단과 상점 설정을 확인한다. [공식: 결제제품 및 계약 과정](https://docs.tosspayments.com/guides/v2/get-started/payment-products)

사업자 정보, 실제 판매상품, 고객 문의 경로, 이용약관·개인정보 처리방침, 취소·반품 안내, 영수증, 에스크로 적용 여부, 기록 보관 기준을 출시 준비 항목으로 둔다. 업종별 의무와 적용 기간은 사업 모델이 정해진 뒤 담당자가 확인해 정책표에 근거를 기록한다. 이 문서의 임의 숫자를 법정 기한으로 사용하지 않는다.

## 13. 다른 사업에도 무엇을 재사용할 수 있는가

| 사업 | 공통으로 쓰는 결제 업무 | 추가해야 하는 사업 규칙 |
| --- | --- | --- |
| 실물 쇼핑몰 | 주문금액 검증, 승인·취소, 거래·대사 | 재고, 배송, 반품, 배송비 |
| 디지털 콘텐츠 | 같은 수납·환불 흐름 | 접근권 발급, 사용 여부, 권리 회수 |
| 예약·티켓 | 같은 수납·환불 흐름 | 좌석 확보, 이용일, 노쇼, 취소 시점 |
| 정기 구독 | 개별 청구의 결제·취소·대사 | 청구 주기, 이용 기간, 갱신, 실패 재청구, 해지 |
| 여러 판매자의 마켓 | 구매자 결제·취소 | 판매자별 배분, 수수료, 지급 보류, 판매자 지급 |

자동결제는 빌링키를 발급받아 청구하는 별도 흐름이다. **빌링키가 있다는 사실과 구독이 정상 이용 중이라는 사실은 다르다.** 청구 일정·실패 대응·해지 시점은 사업자가 기획해야 한다. [공식: 자동결제](https://docs.tosspayments.com/resources/glossary/billing)

마켓의 판매자 지급은 PG가 우리 사업자에게 정산하는 일과 구분한다. 판매자 관리와 지급대행은 별도 서비스·계약 범위로 검토한다. [공식: 지급대행](https://docs.tosspayments.com/resources/glossary/payout)

공통화할 것은 “누구의 어떤 청구에 대해 얼마를 수납·반환했는가”다. 배송 취소 조건이나 구독 해지 정책까지 모든 사업에서 동일하게 만들 필요는 없다.

## 14. 이 프로젝트의 첫 구현 범위 제안

**국내 단일 판매자·KRW·일회성 카드/간편결제·주문 1건 전액 수납**을 첫 기준으로 제안한다. 결제 UI 후보는 토스의 주문서형 결제다. 현재 제품 구분은 [공식 결제제품 비교](https://docs.tosspayments.com/guides/v2/get-started/payment-products)를 따른다.

| 단계 | 포함할 내용 | 완료 기준 |
| --- | --- | --- |
| 도메인·기획 | 주문·결제·환불·제공의 책임, 상태, 금액 규칙 | 정상·실패 시나리오의 처리 결과 설명 가능 |
| 첫 결제 범위 | 주문 연결, 금액 검증, 승인·조회, 전액 취소, 중복 방지 | 결제 및 취소 결과를 근거와 함께 재현 |
| 운영 가능한 범위 | 웹훅, 응답 유실 복구, 감사 이력, 수동 대사, 고객 조회 | 누락·불일치 건을 발견하고 해결 가능 |
| 이후 확장 | 부분 취소, 할인 배분, 가상계좌, 쿠폰·포인트 | 추가 정책과 시나리오를 먼저 확정 |
| 별도 사업 확장 | 구독, 다중 판매자 지급, 해외결제 | 해당 업종·계약·통화·제공 규칙 별도 설계 |

첫 범위에서 반품·부분 취소를 자동화하지 않더라도, 실제 판매를 시작하려면 고객 요청을 처리할 운영 절차가 있어야 한다. “자동화 제외”와 “고객 응대 제외”는 다르다.

다음 산출물은 [정책 결정표](payment-policy-decisions.md)를 구체적인 사업에 맞게 채운 뒤 작성할 유스케이스 명세와 논리 데이터 모델이다. 이 문서의 개념명을 그대로 테이블로 만들기보다, [실무 시나리오](payment-scenarios.md)를 설명할 수 있는지 먼저 확인한다.
