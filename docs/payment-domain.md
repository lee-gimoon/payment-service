# 결제 서비스 개발 계획과 기본 개념

## 1. SDLC를 애자일 방식으로 진행합니다

**SDLC(소프트웨어 개발 생명주기)**는 소프트웨어의 기획부터 운영·개선까지 전체 과정을 설명하는 개념입니다.

```text
기획 → 요구사항 정의 → 설계 → 구현 → 테스트 → 배포 → 운영·피드백 → 개선
```

**이 프로젝트는 SDLC를 애자일(Agile) 방식으로 진행합니다.** 작은 기능 단위로 위 과정을 반복하고, 실제로 사용해본 결과에 따라 다음 작업을 조정합니다. 매번 필요한 요구사항과 설계를 정리하고, 동작하는 기능을 완성하는 것이 기준입니다. [애자일 원칙](https://agilemanifesto.org/iso/ko/principles.html)

## 2. 무엇을 만들고, 어디까지 구현하나요?

목표는 **고객이 주문하고 카드로 결제한 뒤, 그 결과를 확인할 수 있는 결제 서비스**를 만드는 것입니다.

- **사용자와 문제:** 고객은 결제가 됐는지 확인하고 싶고, 판매자는 어떤 주문의 결제가 완료됐는지 정확히 알아야 합니다.
- **첫 MVP(최소 기능 제품):** 티셔츠 1장 주문 → 토스페이먼츠 테스트 결제 → 서버 승인 → 결과 조회까지 연결합니다.
- **학습용 범위:** 상품은 티셔츠 1종, 수량은 1장, 금액은 10,000원으로 고정합니다. 독립 결제 서비스 안에 예제용 최소 주문 기능을 함께 둡니다.
- **나중에 검토할 기능:** 회원가입·로그인, 상품 관리, 배송 연동, 부분 취소, 정산 관리입니다. 실제 사용자에게 공개하기 전에는 인증과 주문 접근 권한을 포함한 운영 요구사항을 별도로 갖춰야 합니다.

현재 코드는 Java 21, Spring Boot, JPA, PostgreSQL, Flyway 등의 기본 설정과 애플리케이션 진입점까지 준비되어 있습니다. 주문·결제 기능과 테스트 화면은 아직 구현하지 않았으며, 아래 내용은 앞으로의 개발 계획입니다.

## 3. 구현 전에 알아둘 결제 개념

여기서 **도메인**은 “결제 업무에서 사용하는 개념과 규칙”이라는 뜻입니다.

### 3.1. 우리가 만들 예시

티셔츠 한 장을 **10,000원**에 파는 쇼핑몰을 생각해봅시다. 배송비와 할인은 없고, 고객은 카드로 결제합니다.

고객은 티셔츠를 주문하고, 결제하고, 나중에 배송받습니다. 우리는 이 과정에서 **어떤 주문에 대해 결제가 완료됐는지 기록하는 기능**을 먼저 만들려고 합니다.

### 3.2. 토스페이먼츠는 어떤 역할을 하나요?

결제에는 다음 참여자가 있습니다.

| 참여자 | 하는 일 |
| --- | --- |
| 고객 | 상품을 고르고 카드로 결제합니다. |
| 우리 쇼핑몰 | 주문과 가격을 저장하고, 결제를 요청하고, 결과를 기록합니다. |
| 토스페이먼츠 | 쇼핑몰과 카드사 사이에서 결제 처리를 연결합니다. |
| 카드사 | 카드 사용자의 인증과 결제 승인 등을 처리합니다. |

이때 토스페이먼츠 같은 결제 대행사를 **PG**라고 부릅니다. 우리 쇼핑몰은 토스페이먼츠와 연동해서 카드 결제를 받을 수 있습니다. [토스 공식 설명](https://docs.tosspayments.com/resources/glossary/card-payment)

### 3.3. 주문부터 결제 완료까지

1. **고객이 주문합니다.** 우리 서버에 “티셔츠 1장, 10,000원, 결제 대기”로 저장합니다.
2. **결제 화면을 엽니다.** 고객이 결제하기 버튼을 누르면 토스페이먼츠의 결제 화면으로 진행합니다.
3. **고객이 카드 인증을 합니다.** 카드 앱에서 비밀번호 등을 입력합니다. 아직 우리 쇼핑몰의 결제 처리가 끝난 것은 아닙니다.
4. **우리 서버가 결제 승인을 요청합니다.** 저장된 주문과 결제금액이 맞는지 확인하고 토스페이먼츠에 승인을 요청합니다.
5. **승인 결과를 확인하고 저장합니다.** 결제가 성공한 것을 확인하면 해당 주문을 “결제 완료”로 기록하고 고객에게 보여줍니다.

**카드 인증을 마친 것과 결제가 최종 완료된 것은 구분해야 합니다.** 우리 서버가 승인 결과를 확인하는 단계까지 있어야 합니다. [토스 공식 결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

### 3.4. 결제했다고 배송과 입금까지 끝난 건가요?

주문 하나에도 서로 다른 일이 진행됩니다.

| 개념 | 확인하려는 것 | 티셔츠 예시 |
| --- | --- | --- |
| 주문 | 무엇을 얼마에 구매했나요? | 티셔츠 1장, 10,000원 |
| 결제 | 고객의 결제가 완료됐나요? | 카드 결제 승인 완료 |
| 상품 제공 | 고객에게 상품을 전달했나요? | 티셔츠 배송 완료 |
| 정산 입금 | 판매대금이 사업자 계좌에 들어왔나요? | 수수료 등을 반영한 금액 입금 |

**결제 완료와 상품 제공 완료:** 월요일에 결제하고 수요일에 티셔츠를 받는다면, 월요일에는 결제만 완료된 상태입니다. 결제 후 배송에 문제가 생기면 “결제 완료, 배송 문제 발생”으로 기록하고 해결해야 합니다.

온라인 강의라면 배송 대신 이용권 발급이 상품 제공에 해당합니다. 결제는 성공했지만 이용권 발급이 실패할 수도 있습니다.

**결제 완료와 정산 입금:** 고객이 월요일에 카드로 결제해도, 사업자 계좌에는 계약에서 정한 정산 일정에 따라 대금이 들어옵니다. 결제금액에서 수수료 등이 반영되므로 고객이 결제한 금액과 사업자가 받는 금액도 다를 수 있습니다. [토스 공식 정산 설명](https://docs.tosspayments.com/resources/glossary/settlement)

날짜를 임의로 정해보면 다음과 같습니다. 실제 정산일은 상점 계약에 따라 달라집니다.

| 시점 | 고객 결제 | 상품 배송 | 사업자 정산 입금 |
| --- | --- | --- | --- |
| 월요일 | 완료 | 준비 중 | 대기 |
| 수요일 | 완료 | 완료 | 대기 |
| 계약에 따른 정산일 | 완료 | 완료 | 입금 확인 |

그래서 **결제 상태, 배송 상태, 정산 상태를 따로 기록**합니다. 지금은 이 세 가지가 서로 다른 일이라는 것만 이해하면 됩니다.

### 3.5. 고객이 취소하면 어떻게 하나요?

아직 티셔츠를 보내지 않았다고 가정해봅시다.

- **결제 전 취소:** 주문을 취소하면 됩니다. 받은 돈이 없으므로 돌려줄 돈도 없습니다.
- **결제 후 취소:** 주문 취소와 함께, 이미 결제한 10,000원을 돌려주는 처리가 필요합니다.

결제 후에는 우리 서버가 토스페이먼츠에 결제 취소를 요청하고 결과를 확인합니다. 우리 DB의 주문 상태만 “취소”로 바꾼다고 카드 결제까지 취소되는 것은 아닙니다.

PG에서 취소를 처리한 뒤에도 고객 카드에 반영되기까지는 시간이 걸릴 수 있습니다. [토스 공식 취소 설명](https://docs.tosspayments.com/guides/v2/cancel-payment)

## 4. 작은 기능 단위로 반복해서 구현합니다

한 번의 반복마다 **직접 실행하고 확인할 수 있는 기능**을 만듭니다. 아래는 초기 우선순위이며, 각 반복의 피드백에 따라 범위와 순서를 조정합니다. 한 번에 끝내기 어렵다면 더 작은 기능으로 나눕니다.

| 반복 | 사용자에게 제공할 기능 | 구현할 내용 | 완료 기준 |
| --- | --- | --- | --- |
| 1. 주문 생성·조회 | 주문을 만들고 주문번호로 확인합니다. | 최소 주문 모델, DB 마이그레이션, 생성·조회 API | 10,000원 주문이 DB에 저장되고, 조회 결과가 일치하며, 없는 주문은 오류로 응답합니다. |
| 2. 테스트 결제 — 첫 MVP | 주문에 대해 카드 결제를 진행하고 결과를 확인합니다. | 최소 주문·결제·결과 화면, 토스 테스트 연동, 서버 금액 검증, 승인 결과 저장·조회 | 테스트 결제 성공과 명확한 실패를 구분하고, 금액 불일치를 거부하며, 중복 요청과 응답 유실에도 결과를 잘못 확정하지 않습니다. |
| 3. 전액 취소 | 결제한 주문을 전액 취소하고 결과를 확인합니다. | 취소 요청·결과 조회, PG 취소 연동, 취소 가능 상태 검증 | PG 취소 성공을 확인한 뒤 취소 결과를 저장하고, 중복 취소나 통신 오류를 확인 없이 성공으로 처리하지 않습니다. |
| 4. 결과 확인·복구 개선 | 처리 중인 결제 결과를 나중에 확인할 수 있습니다. | PG 결과 재조회 자동화, PG와 DB 결과 불일치 복구, 오류 로그 개선 | PG 처리 후 DB 저장 실패나 통신 끊김을 재현하고, 최종 결과가 일치하도록 복구되는지 확인합니다. |

**결제의 기본 검증은 2차 반복부터 포함합니다.** 서버에 저장한 주문금액을 기준으로 승인 요청을 검증하고, 같은 주문에 대한 중복·동시 요청을 제어합니다. 통신 시간 초과처럼 결과가 불명확한 경우에는 “확인 필요”로 남기고 PG 결과를 조회해 확인합니다. PG 승인 후 DB 저장에 실패하는 경우도 복구할 수 있도록 요청 식별 정보를 보관합니다. 4차 반복에서는 이 확인·복구 작업을 자동화하고 보강합니다.

## 5. 지금 시작할 작업: 1차 반복

**사용자 요구:** “티셔츠 한 장을 주문하고, 주문번호로 주문 내용을 확인하고 싶다.”

이번 반복에서는 다음 범위만 먼저 구체화합니다. API 경로는 우리 서비스의 초기 설계안입니다.

| 항목 | 이번에 정할 내용 |
| --- | --- |
| 업무 규칙 | 티셔츠 1장, 10,000원으로 주문합니다. 가격은 서버에서 결정하고, 주문번호는 서버에서 생성합니다. |
| 사용자 흐름 | 주문 생성 요청 → 주문번호 확인 → 해당 주문 조회 |
| 화면 | 우선 API 호출로 확인합니다. 실제 결제에 필요한 최소 화면은 2차 반복에서 추가합니다. |
| API | `POST /orders`: 주문 생성 후 `201` 응답. `GET /orders/{orderId}`: 주문 조회 후 `200` 응답, 없는 주문은 `404` 응답. |
| 데이터 | 주문번호, 상품명, 수량, 주문금액, 생성 시각을 저장합니다. 결제 기록과 결제 상태는 2차 반복에서 설계합니다. |
| 구현 구조 | 기존 Spring Boot 프로젝트에 Controller → Service → Repository 흐름과 주문 엔티티, Flyway 마이그레이션을 추가합니다. |
| 검증 | 주문 생성·조회, 서버가 정한 금액 저장, 잘못된 요청 거부, 없는 주문 조회를 테스트합니다. |

1차 반복은 **생성 API에서 받은 주문번호로 저장된 주문을 다시 조회할 수 있을 때** 완료합니다. 직접 호출해보며 응답에 필요한 정보가 충분한지 확인하고, 발견한 문제를 다음 작업에 반영합니다.

## 6. 매 반복을 진행하는 방법

| 순서 | 할 일 |
| --- | --- |
| 기획·요구사항 | 이번에 해결할 사용자 문제, 포함할 기능, 완료 기준을 짧게 적습니다. |
| 설계 | 해당 기능의 사용자 흐름, 필요한 화면, API 요청·응답, DB와 상태 변경 규칙을 정합니다. |
| 구현 | 정한 기능을 화면 또는 API부터 DB까지 연결합니다. |
| 테스트 | 정상 흐름과 해당 기능의 실패·중복 요청 등 주요 예외를 검증합니다. |
| 실행·배포·운영 확인 | 처음에는 로컬에서 직접 실행합니다. 첫 MVP부터 접근을 제한한 테스트 환경에 배포해 기능과 로그를 확인하며, 테스트 키로 검증합니다. |
| 피드백·개선 | 사용해본 결과와 남은 문제를 기록하고, 다음 반복의 우선순위를 다시 정합니다. |

각 반복은 **완료 기준 충족, 관련 테스트 통과, 로컬 또는 테스트 환경에서의 동작 확인, 문서 갱신**까지 마칩니다. 배포한 기능은 로그와 오류를 확인하고, 발견한 문제를 다음 반복에 반영합니다.

이 문서는 한 파일로 유지합니다. 현재 반복의 설계는 구현 전에 구체화하고, 다음 반복은 목표와 완료 기준을 중심으로 관리합니다. 진행하면서 확정한 규칙과 변경 이유를 해당 항목에 반영합니다.
