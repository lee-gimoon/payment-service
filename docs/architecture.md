# 아키텍처

주문을 만들 때 서버가 `products` 테이블에 저장된 가격으로 총액을 계산한다. 구매자가 토스 결제창에서 결제수단 인증 절차를 마치고 성공 화면으로 돌아오면, 서버가 토스에 최종 승인을 요청하고 결과를 저장한다. 여기서 '인증'은 이 서비스의 회원 로그인이 아니라 토스 결제창에서 카드·간편결제 수단의 사용을 확인하는 절차다. 원화(`KRW`) 주문과 카드·간편결제 테스트 거래만 지원하며 토스 테스트 키만 사용할 수 있다.

## 데이터 모델

| 모델 / 테이블 | 책임 |
| --- | --- |
| `Product` / `products` | V1에서 등록한 상품 10개의 이름·분류·가격 등을 저장한다. 새 주문에는 `active = true`인 상품만 사용한다. |
| `PurchaseOrder` / `purchase_orders` | 주문번호, 주문 생성 시 계산한 총액·통화·총수량, 결제창에 표시할 요약명, 주문 상태를 저장한다. |
| `OrderItem` / `purchase_order_items` | 주문에 포함된 상품 ID(`products.id`), 주문 당시의 상품명·단가·사이즈·수량과 항목 순서를 저장한다. |
| `PaymentAttempt` / `payment_attempts` | 결제창을 열기 전에 생성하며, 결제창 취소·실패와 이후 승인 처리 상태를 기록한다. |
| `Payment` / `payments` | 토스 승인 API를 호출하기 전에 `PROCESSING`으로 생성하는 결제 거래다. 결제 키·시도 ID·요청 금액·통화와 나중에 받은 토스 응답을 저장한다. |

결제창을 열기 전에 `PaymentAttempt`를 만든다. 구매자가 토스 결제창에서 결제수단 인증을 마치고 성공 화면으로 돌아오면 브라우저가 서버에 승인을 요청한다. 서버는 중복 요청을 검사한 뒤 `Payment`를 `PROCESSING`으로 먼저 저장하고 토스 승인 API를 호출한다. 응답을 받으면 이미 만든 `Payment`에 승인 결과를 기록한다.

결제창에서 인증을 취소하거나 실패해 서버 승인 요청을 보내지 않으면 `payment_attempts` 행만 남고 `payments` 행은 생기지 않는다. 승인 요청으로 넘어가면 `payments.attempt_id`에 해당 `payment_attempts.id`를 저장한 결제 행을 하나 만든다. 승인이 명확히 실패해 다시 결제할 때는 새 `PaymentAttempt`를 만들고, 승인 단계에 도달하면 새 `Payment`를 만든다. 따라서 같은 주문에 여러 시도와 실패한 거래가 남을 수 있다. `payments.attempt_id`는 중복을 허용하지 않으므로 동일한 시도 ID로 결제 행을 두 개 만들 수 없다.

주문 요청은 상품 ID·사이즈·수량만 받으며 가격은 받지 않는다. `OrderService`가 판매 중인 상품의 DB 가격으로 총액을 계산하고 주문과 항목을 한 트랜잭션에서 저장한다. 이후 주문 금액은 변경하지 않는다. 주문 당시 상품명과 단가는 `OrderItem`에 별도로 저장하고, 주문 화면은 이 저장값을 보여준다.

테이블과 초기 상품 데이터는 [V1 마이그레이션](../src/main/resources/db/migration/V1__initial_schema.sql)이 만든다. JPA는 테이블을 생성하지 않고 엔티티와 테이블이 일치하는지 검증한다.

## 결제 승인 흐름

브라우저는 서버에 주문과 결제 시도 생성을 요청한 뒤 토스 결제창을 연다. 구매자가 결제창에서 결제수단 인증을 마쳐도 결제는 아직 확정되지 않는다. 성공 화면으로 돌아온 브라우저가 `POST /payments/confirm`을 호출하면 서버가 다음 순서로 처리한다. `PaymentService.confirm()`은 이 순서를 조정하며 자체 DB 트랜잭션은 열지 않는다.

1. `PaymentPreparationService.prepare()`는 DB 트랜잭션에서 주문 행을 잠그고 요청 금액과 중복 결제를 검사한다. 결제 시도를 `PROCESSING`으로 바꾸고 같은 상태의 `payments` 행을 만든 뒤 커밋하며 주문 잠금을 푼다.
2. `TossPaymentClient.confirm()`은 저장한 주문번호·결제 키·금액으로 토스 승인 API를 호출한다. 토스 응답을 기다리는 동안 DB 트랜잭션이나 주문 잠금은 유지하지 않는다.
3. `PaymentSettlementService.record()`는 별도 DB 트랜잭션에서 토스 결과를 결제 거래와 시도에 기록한다. 검증된 승인 성공이면 같은 트랜잭션에서 주문 상태를 `CONFIRMED`로 바꾼다.
4. 승인 결과를 알 수 없어 `UNKNOWN`으로 기록했다면, 같은 서버 요청 안에서 `TossPaymentClient.lookup()`으로 해당 결제를 한 번 조회하고 `record()`로 조회 결과를 다시 저장한다.

서버는 토스 응답의 주문번호·결제 키·금액·통화가 저장된 결제 정보와 일치하는지 확인한다. 토스 응답의 상태가 `DONE`이고 결제수단이 지원 대상이며 승인 시각도 있어야 성공으로 확정한다. 토스 승인 요청의 응답을 받지 못했거나 응답을 검증할 수 없다면 곧바로 실패로 처리하지 않는다. 재조회에서 검증된 성공은 `SUCCEEDED`, 확인된 `ABORTED`·`EXPIRED`는 `FAILED`로 저장한다. 여전히 결과를 판단할 수 없거나 승인 정보가 일치하지 않으면 `REVIEW_REQUIRED`로 남기며 자동 취소 요청은 하지 않는다.

## 중복 요청과 동시성

`POST /orders`에는 같은 장바구니 요청을 하나의 주문으로 합치는 기능이 없다. 두 탭에서 각각 주문을 만들면 서로 다른 주문번호가 생성될 수 있다. 아래의 중복 결제 방지는 **같은 주문번호**에 적용된다.

- 결제 시도 생성과 승인 준비는 먼저 해당 주문 행에 DB 잠금을 건다. 같은 주문의 두 요청이 동시에 "진행 중인 결제가 없다"고 판단하지 않도록 한 번에 하나씩 검사한다. 잠금은 각 DB 트랜잭션이 끝날 때 풀린다.
- 결제 시도는 결제창을 열기 전에 생성한다. 아직 진행 중인 결제 거래가 없다면 같은 주문에서 시도를 여러 번 만들 수 있지만, 시도 생성만으로 토스에 승인 요청을 보내지는 않는다.
- 승인 준비에서는 요청한 결제 키에 연결된 거래를 먼저 찾는다. 같은 결제 키·주문·시도의 재요청이면 저장된 주문 결과를 반환하고 토스 승인을 다시 호출하지 않는다. 다른 결제 키로 요청했더라도 같은 주문에 `FAILED`가 아닌 거래가 있으면 거부한다.
- 새 결제 거래를 만들려면 해당 주문의 결제 시도가 `STARTED`여야 한다. 이미 처리한 시도나 다른 주문의 시도는 사용할 수 없다. 명확히 `FAILED`로 끝난 거래가 있으면 새 시도로 재시도할 수 있다.
- DB는 결제 키와 시도 ID의 중복, 시도와 거래의 주문 불일치, 한 주문에 `FAILED`가 아닌 거래가 둘 이상 생기는 일을 제약으로 막는다. 토스에는 같은 승인 요청을 식별할 수 있도록 시도 ID를 `Idempotency-Key`로 전달한다.
- `PurchaseOrder`, `PaymentAttempt`, `Payment`의 `@Version`(낙관적 잠금)은 **이미 있는 같은 행**을 동시에 수정할 때 충돌을 감지한다. 주문 생성 중복이나 같은 주문의 중복 승인 요청을 막는 주된 장치는 아니다.
- 브라우저의 인증 취소·실패 알림은 아직 `STARTED`인 시도에만 반영한다. 늦게 도착한 알림이 서버에 저장한 승인 상태를 덮어쓰지 않는다.

## 상태

주문은 생성 직후 `PENDING_PAYMENT`다. 검증된 결제 승인 성공을 DB에 저장할 때 같은 주문을 `CONFIRMED`로 바꾼다. 결제 거래가 아직 없으면 주문 조회 응답의 `payment.status`는 `READY`이며, 이 상태를 가진 `payments` 행은 만들지 않는다.

| 결제 거래 상태 | 의미 / 후속 동작 |
| --- | --- |
| `PROCESSING` | 승인 요청을 준비해 DB에 저장한 상태다. 이 주문의 새 결제를 허용하지 않는다. |
| `SUCCEEDED` | 토스의 승인 성공을 검증하고 저장한 상태다. 주문도 `CONFIRMED`가 된다. |
| `FAILED` | 명시적 결제 거절이나 확인된 `ABORTED`·`EXPIRED` 상태다. 같은 주문에서 새 시도로 다시 결제할 수 있다. |
| `UNKNOWN` | 토스 승인 여부를 알 수 없어 기록한 상태다. 같은 서버 요청에서 한 번 재조회하며, 새 결제는 허용하지 않는다. |
| `REVIEW_REQUIRED` | 재조회에서 승인 정보가 일치하지 않거나 성공·실패를 확정할 수 없어 토스 결제 내역과 DB 기록을 사람이 대조해야 하는 상태다. |

결제 시도 상태는 `STARTED`, `AUTH_CANCELED`, `AUTH_FAILED`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `REVIEW_REQUIRED`다. 거래가 `UNKNOWN`이면 시도는 `PROCESSING`으로 유지된다. `AUTH_CANCELED`는 결제창 닫기나 결제수단 인증 취소를 뜻하며, 이미 승인된 결제의 취소가 아니다.

## 실패와 복구 범위

DB 저장과 토스 승인은 하나의 트랜잭션으로 묶을 수 없다. 예를 들어 토스에서 승인한 뒤 서버가 결과를 DB에 저장하지 못하면, 실제 결제 결과와 저장된 상태가 다를 수 있다. DB 저장이 롤백되어도 토스 승인이 자동으로 취소되지는 않는다.

서버 중단이나 저장 장애로 거래가 `PROCESSING` 또는 `UNKNOWN`에 남을 수 있다. 이미 저장된 결제 키·주문·시도로 `/payments/confirm`을 다시 호출하면 저장된 주문 결과를 반환한다. `GET /orders/{orderId}`와 화면의 "주문 내역 새로고침"은 DB만 읽고 토스를 다시 조회하지 않는다. 이 동작만으로 미확정 거래가 자동 복구되지는 않는다.

오래 미확정 상태로 남은 거래나 `REVIEW_REQUIRED` 거래는 주문번호·결제 키·시도 ID와 토스 결제 내역을 대조해 수동으로 확인해야 한다. 서버 재시작 후 자동 복구, 주기적 대조, 웹훅 처리, 수동 결과 반영용 관리자 API는 구현하지 않았다. 승인 결과가 불확실해 같은 요청에서 토스를 재조회했을 때 `CANCELED`·`PARTIAL_CANCELED`가 반환되면 `REVIEW_REQUIRED`로 기록한다. 승인 완료 후 취소·환불 상태를 다시 확인하는 기능은 없다.

서비스 사용자 로그인과 주문 조회 권한 검사, 배송, 재고 예약·차감, 상품 관리 API, 결제 취소·환불도 구현하지 않았다.

API 요청과 응답 계약은 [API 문서](api.md)를 참고한다.
