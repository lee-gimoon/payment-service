# Architecture

상품 카탈로그에서 주문 금액을 확정하고 토스 결제창의 인증 결과를 서버에서 승인하는 구조다. 현재 지원 범위는 KRW 주문과 카드·간편결제 테스트 거래다. 설정은 테스트 키만 허용한다.

## 데이터 모델

| 모델 / 테이블 | 책임 |
| --- | --- |
| `Product` / `products` | 현재 판매 정보와 서버 가격. 판매 중지 상품은 `active = false`로 제외하고 과거 주문의 참조는 유지한다. |
| `PurchaseOrder` / `purchase_orders` | 주문번호, 확정 금액·통화, 총수량, 결제창용 요약명, 주문 상태. |
| `OrderItem` / `purchase_order_items` | 상품 참조와 주문 당시 이름·단가·사이즈·수량. 요청 순서대로 보존한다. |
| `PaymentAttempt` / `payment_attempts` | 결제창을 열기 전 생성하는 시도. 인증 취소·실패와 이후 승인 처리 결과를 기록한다. |
| `Payment` / `payments` | 인증 후 승인 요청을 준비한 거래. 결제 키, 시도 ID, 요청 금액·통화와 확인된 PG 결과를 보관한다. |

주문에는 여러 시도와 거래가 연결될 수 있다. 한 시도에는 거래가 최대 하나 연결된다. 명확히 실패한 거래도 삭제하지 않고 이후 시도와 함께 이력으로 남긴다.

주문 요청은 상품 ID·사이즈·수량만 받는다. `OrderService`가 판매 중인 상품의 현재 가격으로 합계를 계산하고 주문과 항목을 한 트랜잭션에서 저장한다. 생성된 주문 금액은 변경하지 않으며, 상품 이름·가격 변경과 판매 중지는 과거 항목의 스냅샷에 영향을 주지 않는다.

스키마와 초기 상품 데이터는 [V1 마이그레이션](../src/main/resources/db/migration/V1__initial_schema.sql)이 정의한다. JPA는 스키마를 생성하지 않고 엔티티와 테이블의 일치를 검증한다.

## 승인 처리

`PaymentService.confirm()`은 DB 트랜잭션을 열지 않는 조정자다. 저장 작업은 별도 서비스의 트랜잭션으로 실행한다.

```text
PaymentPreparationService.prepare()
  주문 잠금 → 요청 금액 검증 → 중복 확인
  → 거래 생성 + 시도 PROCESSING → 커밋·잠금 해제

TossPaymentClient.confirm()
  저장된 금액과 시도 ID로 외부 승인 요청

PaymentSettlementService.record()
  거래 + 시도 결과 반영 → 성공이면 주문 CONFIRMED → 커밋

결과가 UNKNOWN인 경우에만:
  TossPaymentClient.lookup() → 같은 거래를 한 번 조회
  → PaymentSettlementService.record() → 최종 결과 커밋
```

결제창 인증 성공과 서버 승인 완료는 구분한다. 승인 성공은 주문번호·결제 키·금액·통화가 일치하고, 지원 결제수단의 `DONE` 응답에 승인 시각이 있을 때 확정한다.

승인 응답 유실, 통신 오류, 불완전하거나 검증에 실패한 응답은 실패로 단정하지 않는다. `UNKNOWN`을 먼저 저장하고 같은 요청 안에서 한 번 재조회한다. 재조회로도 확정할 수 없거나 승인 정보가 불일치하면 `REVIEW_REQUIRED`로 남긴다. 자동 취소 요청은 하지 않는다.

PG 호출을 기다리는 동안 준비 트랜잭션과 주문 잠금은 이미 종료되어 있다. HTTP 호출은 요청 스레드에서 동기적으로 실행하며, 결과 저장은 새 트랜잭션에서 수행한다. 주문 조회는 저장된 DB 결과만 읽는다.

## 중복과 동시 처리

- 시도 생성과 승인 준비는 주문 행의 쓰기 잠금으로 직렬화한다.
- 신규 승인에는 기존 `STARTED` 시도의 ID가 필수다. 다른 주문의 시도나 이미 진행된 시도로 새 거래를 만들 수 없다.
- 같은 결제 키·주문·시도의 재요청은 외부 승인을 반복하지 않고 현재 주문 응답을 반환한다. 같은 키를 다른 주문·시도에 사용하면 충돌로 거부한다.
- 토스 승인 요청의 `Idempotency-Key`에는 시도 ID를 사용한다.
- DB는 결제 키·시도 ID의 유일성, 시도와 거래의 주문 일치, 주문당 `FAILED`가 아닌 거래 최대 하나를 보장한다. 주문·시도·거래의 버전 검사도 동시 갱신 충돌을 감지한다.
- 인증 취소·실패 이벤트는 `STARTED` 시도에만 반영한다. 늦은 브라우저 이벤트가 서버 승인 상태를 덮어쓰지 않는다.

## 상태

주문 상태는 `PENDING_PAYMENT`와 `CONFIRMED`다. 검증된 승인 성공을 저장할 때 주문을 확정한다.

| 결제 상태 | 의미 / 후속 동작 |
| --- | --- |
| `READY` | 거래가 없는 주문 응답의 상태. DB 결제 행에는 저장하지 않는다. |
| `PROCESSING` | 승인 준비가 커밋된 상태. 새 결제를 허용하지 않는다. |
| `SUCCEEDED` | 검증된 승인 성공. 주문이 확정된다. |
| `FAILED` | 명시적 카드 거절 또는 확인된 `ABORTED`·`EXPIRED`. 같은 주문에서 새 시도를 허용한다. |
| `UNKNOWN` | 결과가 불확실하여 즉시 재조회하기 전에 저장하는 상태. 새 결제를 허용하지 않는다. |
| `REVIEW_REQUIRED` | 자동으로 결과를 확정하지 못한 상태. 수동 확인이 필요하다. |

시도 상태는 `STARTED`, `AUTH_CANCELED`, `AUTH_FAILED`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `REVIEW_REQUIRED`다. 거래의 `UNKNOWN` 동안 시도는 `PROCESSING`으로 유지된다. `AUTH_CANCELED`는 결제창 닫기·인증 취소 기록이며 승인된 결제의 취소가 아니다.

## 실패 경계와 운영 범위

DB와 PG 처리는 하나의 원자적 작업이 아니다. 준비가 커밋된 후 외부 호출이나 프로세스가 중단될 수 있고, PG 승인이 완료되어도 결과 저장이 실패할 수 있다. 결과 저장의 롤백은 토스 승인을 되돌리지 않는다.

프로세스 중단이나 저장 장애로 `PROCESSING`·`UNKNOWN`이 남을 수 있다. 재시작 후 자동 복구, 주기적 대조, 웹훅 처리는 구현하지 않았다. 중복 승인 요청과 화면 새로고침은 DB 결과만 반환하므로 이런 거래를 자동 복구하지 않는다. 장시간 미확정 거래와 `REVIEW_REQUIRED`는 저장된 주문번호·결제 키·시도 및 PG 기록을 대조해 수동으로 확인해야 한다. 수동 결과 반영용 관리자 API도 제공하지 않는다.

현재 범위에는 구매자 인증·주문 접근 권한, 배송, 재고 예약·차감, 상품 관리 API, 승인 취소·환불이 없다. 외부에서 취소된 거래가 재조회되면 주문을 자동 변경하지 않고 수동 확인 대상으로 남긴다.

API 요청과 응답 계약은 [API 문서](api.md)를 참고한다.
